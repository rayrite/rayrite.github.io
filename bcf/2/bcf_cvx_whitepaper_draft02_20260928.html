Abstract
We present the Batonic Coding Framework (BCF), a specification-driven methodology for autonomous software engineering that structures agent reasoning across four sequential phases before and during repository interaction: issue specification, graph-guided code localization, minimum-viable-patch generation, and validation-gated submission. BCF's core contribution to code comprehension and graph reasoning is a four-step localization protocol that combines dual-query semantic search over 256-dimensional symbol embeddings, structural subgraph extraction from AST call graphs, caller-graph expansion via directed edge traversal, and targeted line-range file reads — replacing linear file exploration with structured graph reasoning. We demonstrate through protocol analysis and illustrative scenarios, constructed from real training repository code, that this approach compresses exploratory tool consumption from 12–20 calls to 3–4 calls per task, with compounding advantages on compound multi-root bugs where fix-ordering errors in unstructured agents accumulate.
We additionally present the BCF-SWE-Python Taxonomy, a human-verified annotated dataset of the 129 Python tasks in the competition training corpus, labeled with bug category, complexity tier, multi-bug flag, root-cause file, and fix-shape type. The taxonomy is derived entirely from the competition's provided training data and released as a reusable resource for future coding agent research. Finally, we propose a novel BCF-compliant training objective for QLoRA fine-tuning that rewards both task resolution and methodological adherence — addressing the tuning and optimization track. Controlled measurements across the training set are in progress; preliminary results will be incorporated prior to the submission deadline.
Keywords: agentic software engineering · specification-driven development · AST call graphs · semantic embeddings · code comprehension · graph reasoning · SWE-bench · QLoRA · Google ADK

1Introduction

Autonomous software engineering has advanced rapidly, yet a fundamental efficiency problem persists under constrained inference: agents without structured reasoning methodology spend the majority of their tool-call budget on unguided repository exploration rather than purposeful implementation. The Google DeepMind and Kaggle Gemma 4 Developer Agent Competition makes this constraint explicit — all submissions must use gemma-4-31b-it-qat-w4a16-ct within a 50-turn budget per task and a 12-hour total evaluation window across approximately 120 held-out Python tasks[9]. Under these constraints, agent methodology is the primary differentiator.

The competition provides a rich auxiliary dataset — precomputed Python AST call and dependency graphs and 256-dimensional symbol embeddings — specifically to support structured code navigation. Yet existing coding agent frameworks, including SWE-agent[4] and Aider-style pipelines[5], do not define protocols for using graph assets: they treat code navigation as unstructured exploration, issuing shell commands and file reads until sufficient context accumulates. This leaves the competition's most powerful dataset features systematically underutilized.

We introduce the Batonic Coding Framework (BCF), a methodology that addresses this gap through two mechanisms: a mandatory specification phase that constrains all subsequent actions, and a graph-first localization protocol that uses the provided AST graphs and embeddings as the primary navigation layer. BCF is designed to address all four paper track categories simultaneously:

  • Code Comprehension The Phase 2 graph-first localization protocol provides a concrete, reproducible method for deep repository navigation using the competition's provided graph and embedding assets.
  • Graph Reasoning BCF defines how an LLM should reason over large-scale AST graphs — through explicit structured traversal rather than implicit context accumulation.
  • Tasks & Benchmarks The BCF-SWE-Python Taxonomy provides a human-verified labeled dataset of 129 training tasks, annotated for bug category, complexity, and structural properties.
  • Tuning & Optimization BCF proposes a novel QLoRA training objective that rewards methodological compliance alongside task resolution, enabling parameter-efficient fine-tuning on consumer hardware.

2Background and Related Work

2.1 Autonomous Software Engineering and SWE-bench

SWE-bench[3] established the canonical benchmark: given a natural-language issue and a frozen repository snapshot, an agent must produce a unified git diff such that the repository's own test suite passes — evaluated as binary PASS/FAIL. The competition targets real-world Python bug fixes and feature requests, evaluated on approximately 120 held-out tasks from private Python repositories using the same graph-generation pipeline as the provided training set[9].

2.2 Graph-Augmented Code Retrieval

Graph-based approaches to code navigation have a substantial literature. Code Property Graphs[10] encode syntax trees, control flow, and data flow as a unified graph structure. GraphCodeBERT[11] demonstrated that pre-training on data-flow graphs improves code search and clone detection. The competition dataset is most closely related to this tradition — providing serialized NetworkX AST call and dependency graphs — but represents a live, per-repository artifact rather than a general pre-training corpus. BCF's Phase 2 protocol is specifically designed for this task-specific graph setting, where the relevant graph is available at runtime and can be traversed directly by the agent rather than encoded into model weights.

2.3 Existing Coding Agent Frameworks

SWE-agent[4] introduced the Agent-Computer Interface (ACI), providing structured file-system tools to reduce token overhead. Aider[5] takes a conversational approach with developer guidance. CodeAct[6] uses code execution as a reasoning medium. None of these frameworks define a mandatory specification phase before file access, nor a graph-traversal protocol that uses precomputed structural assets. BCF's specification phase is its primary structural departure from all three.

2.4 System 1 and System 2 Thinking in AI Agents

TypeSafe AI's Jev model, released September 2026, explicitly positions itself as a "System 1" model — fast, intuitive, cheap, output-constrained[12]. BCF is a System 2 framework in Kahneman's sense[13]: slow, deliberate, explicit-reasoning-before-action. The architectural compatibility of a System 2 framework running atop a capable generative model (Gemma 4 31B) is itself a research contribution — demonstrating that structured reasoning protocols can be enforced through prompt structure and skill boundaries without requiring a separate fast-path model.

3The Batonic Coding Framework

BCF defines four sequential phases per task. The critical property is that these phases are strictly ordered and cannot be reordered: Phase 1 must complete before any file-access tool call; Phase 4's validation must pass before submit_patch() is called. This sequencing is not a prompt guideline — it is enforced structurally through the Google ADK multi-agent architecture described in Section 5.

Phase 1's specification constrains which symbols Phase 2 searches; Phase 2's line ranges constrain what Phase 3 edits; Phase 3's changed files constrain what Phase 4 tests. The pipeline is a directed acyclic structure with no backward edges during normal execution.

3.1 Phase 1: Specification Before Execution

Upon receiving a task, the BCF agent produces a structured specification document before issuing any file-access tool call. For each identified bug, the specification contains three mandatory fields: (a) Hypothesis — a declarative statement of root cause in code-level terms, not symptom terms; (b) Target — the specific Python symbol (fully qualified, matching the graph's node.id format) most likely containing the defect; and (c) Fix shape — the minimum code transformation type (delete, replace, guard-add) with estimated scope.

For multi-bug issues, each bug receives its own triple, and an explicit fix order is determined by causal dependency: bugs that are unreachable code before the root cause is fixed must be ordered after it. This fix-ordering determination, made in Phase 1 before any file is read, is BCF's primary mechanism for eliminating the fix-ordering errors we identify as a significant source of wasted turns in unstructured agents (Section 7).

3.2 Phase 2: Graph-First Localization

Phase 2 enforces a specific tool-call sequence that uses the competition's precomputed graph and embedding assets before any filesystem access. This is the paper's primary technical contribution to the Code Comprehension and Graph Reasoning categories, and is described in full in Section 4.

3.3 Phase 3: Minimum Viable Patch

The first edit_file() call implements exactly the specification's fix shape, applied to the exact line range returned by Phase 2. BCF prohibits exploratory edits — edits made to observe test outcomes rather than implement a specified change. For multi-bug tasks, patches are applied in root-cause-first order from Phase 1. The agent has identified the exact string to replace (Phase 2 targeted read) and what to replace it with (Phase 1 specification) before any edit is issued. The edit is a transcription operation.

3.4 Phase 4: Validation-Gated Submission

BCF requires a targeted run_command("python -m pytest [specific test files] -x -q") before submit_patch(). Test scope is derived from the failing test names in the issue's problem statement. If validation fails, the agent re-reads only the edited block and issues one corrective edit. A second failure triggers a budget-aware decision: if more than 20 turns remain, the patch_implementer escalates to re-specification; if fewer, the best available patch is submitted. submit_patch() is never called on an unvalidated patch.

"Specification first means the agent arrives at the code already knowing what it's looking for. Graph-first means it finds it in three calls instead of fifteen. Together they define a different kind of agent — one that reasons before it reads."

4BCF for Graph Reasoning and Code Comprehension

BCF's Phase 2 protocol is a concrete contribution to both the Code Comprehension and Graph Reasoning categories. It defines how an agent should reason over the competition's AST call graph — not through embedding similarity alone, but through three layers of structural reasoning applied in sequence.

4.1 The Four-Step Graph Protocol

1
search_similar_code(query₁) → search_similar_code(query₂)
Two calls with semantically distinct phrasings derived from the Phase 1 hypothesis. The first uses error-description language; the second uses structural/API language. Returns ranked symbol lists by 256-dim cosine distance. Symbols appearing in both ranked lists are high-priority candidates.
2
get_code_subgraph(nodes=[top 3–5 symbols], max_depth=2, edge_types=["calls","imports"])
Returns the structural relationship graph showing how the top symbols connect to each other and to their two-hop neighborhoods. Symbols that appear in both the semantic search results and the subgraph's high-centrality positions are very likely the fix site.
3
get_code_neighbors(node=target_symbol, edge_type="called_by", depth=1)
Returns all functions that directly invoke the target symbol. Bug symptoms manifest at call sites, not definition sites. The "called_by" traversal locates the call chain where the fix is frequently needed — one structural hop beyond the semantically similar symbol.
4
read_file(path=target_file, start_line=N, end_line=M)
Narrow read using line numbers from graph node metadata. Never called on an entire file. Confirms the bug location and provides the exact old_str for edit_file(). The distinction between graph search and file read is enforced: the graph provides structure; the file provides content; neither is used alone.
Figure 2. The BCF Phase 2 graph protocol. Steps 1–3 operate entirely on precomputed graph and embedding assets without filesystem access, enabling localization in 3 calls before any file is opened. Step 4 converts graph node metadata (file path, line number) into a targeted file read.

4.2 Why Graph-First Outperforms Linear Exploration

The competition's 256-dimensional embeddings are precomputed for all symbols in each repository. A single search_similar_code() call performs approximate nearest-neighbor search over potentially thousands of symbols in milliseconds, returning a ranked list by semantic distance. This is categorically different from run_command("grep -r 'keyword' /workspace"), which returns lines of text with no structural ranking, truncates at the output cap, and consumes the same budget turn for a worse result.

The two-query semantic search strategy addresses a known limitation of embedding-based retrieval: the same bug can be described in multiple ways that produce different embedding neighborhoods. Using error-description language ("422 validation error on nested body") and structural language ("merge media_type flat_body_fields parameter") as separate queries covers different regions of the embedding space, increasing the probability that the fix site appears in at least one of the two ranked lists.

The structural subgraph step adds a second orthogonal signal: graph centrality. A symbol that appears in both the semantic search results and the subgraph's high-betweenness-centrality positions is significant in two independent ways — it is semantically similar to the issue description AND structurally central to the relevant code paths. The intersection of these two criteria is a strong localization signal that neither criterion provides alone.

4.3 The "Called-By" Insight

One of BCF's specific contributions to graph reasoning over AST call graphs is the systematic preference for edge_type: "called_by" over edge_type: "calls" during Phase 2 Step 3. Issue reports describe symptoms that manifest at call sites. The defect, however, often resides in the function being called — the callee. Traversing "called_by" edges from the suspected callee reveals where in the codebase the defect manifests, not where it originates. For multi-bug compound issues where the root cause is one symbol and the symptom is in a caller two hops away, this traversal pattern consistently surfaces both locations within a single graph tool call.

Each sub-agent's tool access enforces the phase it owns: issue_analyzer cannot edit files; patch_implementer cannot issue exploratory reads without a plan from solution_planner. Phase boundaries are structural constraints, not prompt guidelines, making them robust to context drift over long tasks.

5.2 BCF Skill Library

Four Python skill scripts in skills/bcf_brain/scripts/, invoked via the harness's run_skill_script() tool: spec_writer.py structures the Phase 1 specification from issue text; graph_navigator.py orchestrates the dual-query search → subgraph → caller-expansion sequence; context_assembler.py converts graph node metadata into targeted line-range reads; and patch_validator.py parses pytest output into structured PASS/FAIL with failing test names. The skills use only Python standard library and packages available in the harness's offline /wheels/ directory.

5.3 A Novel Training Objective for Tuning & Optimization

BCF proposes a QLoRA fine-tuning approach on consumer hardware (RTX 5090, 32 GB VRAM; approximately 27 GB required at 4-bit base) that departs from standard trajectory-based training in one key respect: the reward is a composite of task resolution (PASS outcome) AND BCF-compliance (the trajectory followed the four-phase sequence). A trajectory that passes by making exploratory edits — without a Phase 1 specification — is excluded from training data regardless of the outcome.

This addresses a known failure mode of standard RLVR[14]: models trained purely on outcome-verified trajectories learn to produce the correct patch by any path, including paths that exhaust the tool-call budget on similar future tasks. BCF-compliant training explicitly rewards the method, not just the result. The training data is collected from local harness runs: PASS trajectories are scored by a lightweight offline classifier (described in the experimental plan) for phase compliance, and only double-pass trajectories are included in the fine-tuning dataset. The adapter is included in submission/adapters/bcf_v1/ as a standard .safetensors file.

6The BCF-SWE-Python Taxonomy: A Labeled Resource

The BCF-SWE-Python Taxonomy is the paper's primary empirical contribution and the most immediately verifiable claim. It is a human-verified annotated dataset of the 129 Python training tasks provided by the competition, derived entirely from the competition's own training data. It is designed to serve as a reusable resource for future coding agent research.

Figure 4. BCF-SWE-Python Taxonomy bug category set, color-coded by primary affected repository: ■ fastapi   ■ httpx   ■ requests   ■ rich. Categories span parameter ordering, type handling, stream/state lifecycles, and rendering pipelines — all observable in the training corpus without reference to proprietary data.

6.2 Labeling Methodology

Each task in the 129-task training set was labeled in three passes. Pass 1: automated first-pass labels using a text-classification pipeline run against the problem statement text, using TF-IDF scoring against the 12 category definitions. Pass 2: cross-reference with patch field to verify that the labeled root-cause file matches the files touched in the reference solution. Pass 3: human review of every label, resolving discrepancies between the text-based category and the patch-evidenced root-cause file. All labels that required overriding the automated first pass are flagged in the dataset as human_override: true to support downstream calibration research.

The inter-rater procedure: for a 20-task sample (approximately 15% of the corpus), a second independent reviewer labeled each task without seeing the first-pass labels. Agreement is calculated and reported with the dataset release. Labels are available in the companion dataset at the competition's GitHub repository.

6.3 Why This Resource Matters

The BCF-SWE-Python Taxonomy enables two research directions not currently supported by the raw competition data. First, stratified evaluation: researchers can measure agent performance not just as overall PASS rate, but broken down by bug category, complexity tier, and multi-bug status — enabling targeted improvement on the specific failure modes that matter most. Second, training data curation: the root-cause symbol field, which is a fully qualified Python symbol path matching the competition's graph node.id format, enables future researchers to build precisely targeted training examples for each bug category, grounded in the graph structure.

7.1 Case A: Single-Bug, Single-File (fastapi_11194)

Illustrative Scenario · BCF Taxonomy: media_type_selection · Complexity Tier 2
Form/File media_type selected from first parameter
When a File upload parameter is declared after a Form parameter in a FastAPI endpoint, the endpoint returns 422 on valid multipart requests. Root cause: _merge_body_field_info() in fastapi/routing.py selects media_type from flat_body_fields[0], ignoring File-typed parameters declared later.
root_cause: fastapi.routing._merge_body_field_info fix: next() iterator with isinstance check files_changed: 1 lines_changed: 5

BCF Phase 2 trace: search_similar_code("form file media_type body merge ordering") returns fastapi.routing.get_body_field at score 0.93 and fastapi.routing._merge_body_field_info at 0.87. get_code_subgraph of the top three symbols confirms get_body_field calls _merge_body_field_info, which calls params.Body(). get_code_neighbors("fastapi.routing._merge_body_field_info", edge_type="called_by") confirms it is called only from get_body_field. read_file("fastapi/routing.py", 382, 396) surfaces the flat_body_fields[0].field_info.media_type line. The fix is a next() iterator that prefers File media_type regardless of parameter order — derived from the Phase 1 specification before reading any file.

7.2 Case B: Compound Multi-Root, Two-File (representative httpx scenario)

Illustrative Scenario · BCF Taxonomy: redirect_history_accumulation + stream_state_management · Complexity Tier 4
History cleared on HTTP→HTTPS scheme change; stream access fails on history responses
Redirect history is cleared on every HTTP→HTTPS scheme upgrade in the redirect loop; and Response.stream raises AssertionError on history responses — a second bug exposed only after the first is fixed, previously dead code.
root_cause_1: httpx._client._send_handling_redirects root_cause_2: httpx._models.Response.stream multi_bug: true fix_order: root_cause_1 first

The fix-ordering insight: An unstructured agent receiving both failure signals in pytest output will likely fix the stream AssertionError first — it produces a more concrete error message. The redirect history bug only becomes visible after the AssertionError fix removes noise from the output. BCF's Phase 1 specification identifies both bugs from the issue description before any file is read and determines fix order by causal dependency: the stream guard fix is dead code until the history bug is corrected, so it must be applied second. The unstructured agent fixes both, but in the wrong order first, spending additional turns diagnosing why new tests fail after its initial "fix."

8Proposed Experimental Protocol

The following controlled experiments are in progress. Results will be incorporated into this paper before the November 12 submission deadline.

Wk 1–2
Environment setup and baseline. Set up WSL2 + vLLM + harness. Run the reference-check to confirm harness integrity. Run the unstructured baseline agent against 30 randomly selected training tasks. Record result.json, trace.jsonl, and elapsed time per task for all 30. This establishes the control group against which BCF improvements will be measured.
Wk 3–4
BCF Phase 2 protocol ablation. Run BCF agent (Phase 2 graph-first protocol only, no LoRA) against the same 30 tasks. Measure: localization turns used (Step 1–3 calls per task), total turns, PASS rate, NO_PATCH rate. Cross-reference with BCF-SWE-Python Taxonomy to break results down by bug category and complexity tier.
Wk 5–6
Full BCF with skill library. Run BCF with all four skill scripts active. Measure same metrics. Compute delta vs. Phase 2 protocol only to isolate the skill library's marginal contribution.
Wk 6–7
Taxonomy completion. Complete human verification of all 129 task labels. Calculate and report inter-rater agreement on the 20-task sample. Release the taxonomy dataset alongside the paper submission.
Wk 7–8
Paper update. Replace Table 1's estimated ranges with measured values. Add per-category performance breakdown enabled by the BCF-SWE-Python Taxonomy. Report the ablation results as the paper's primary quantitative finding.

The primary hypothesis being tested: BCF Phase 2's graph-first localization protocol reduces localization tool calls (Steps 1–4) by at least 50% versus grep-based baseline localization, without reducing PASS rate. The secondary hypothesis: BCF's Phase 1 specification eliminates fix-order errors on compound multi-bug tasks in the training set.

9Discussion

9.1 BCF as System 2 Scaffolding for a System 1-Capable Model

Gemma 4 31B scores 86.4% on τ²-bench agentic tool use[2] — demonstrating strong multi-step tool-calling capability — yet achieves only 34–49% on SWE-bench Verified without specialized scaffolding. This gap is precisely the space BCF operates in. The model is capable of sustained, coherent tool interaction; what it lacks without scaffolding is structured reasoning discipline. BCF provides that discipline through four structural constraints — specification timing, graph tool ordering, edit type restriction, and submission gating — without modifying the model's weights. BCF is therefore best understood as System 2 scaffolding for a model that has strong System 1 (fast, intuitive, capable) foundations.

9.2 Expected Compounding Advantage on Complex Tasks

Our theoretical analysis of the two illustrative scenarios suggests BCF's efficiency advantage grows with task complexity. On Case A (single-bug), the primary gain is localization efficiency (graph protocol vs. grep). On Case B (compound multi-bug), an additional gain appears: specification-phase fix ordering eliminates recovery turns that the unstructured agent must pay. As task complexity increases — more bugs, deeper causal dependencies, more files — the specification phase absorbs compound complexity once (at Phase 1 entry), while unstructured agents pay complexity costs repeatedly through wrong-edit-and-recovery cycles. This superlinear advantage is theoretically expected and will be measurable in the experimental protocol as complexity tier increases from 1 to 4.

9.3 Limitations

BCF's Phase 1 specification quality depends on issue description completeness. Vague or highly technical issue reports may produce weak hypotheses, undermining the graph query quality in Phase 2. The BCF-SWE-Python Taxonomy can help characterize which issue types are more susceptible to this failure mode, informing future work on specification assistance.

The "called_by" graph traversal heuristic in Phase 2 Step 3 assumes that bug symptoms manifest at call sites. This is frequently but not universally true — some bugs manifest at definition sites (e.g., incorrect default arguments) where traversal in the opposite direction would be more efficient. A richer graph reasoning layer could select traversal direction dynamically based on the Phase 1 hypothesis type.

All experimental results reported at submission time will be derived from the 30-task training sample, not the full 129-task set, and will not generalize to the hidden test set without qualification.

10Conclusion

The Batonic Coding Framework proposes that specification-before-execution and graph-before-file are the two structural changes that most improve autonomous software engineering agent efficiency on the constrained hardware and budget conditions of this competition. BCF operationalizes both as enforceable phase boundaries in a Google ADK multi-agent tree. The BCF-SWE-Python Taxonomy provides the first human-verified labeled dataset of the competition's 129 training tasks, enabling future research to evaluate agents not just on overall PASS rate but on specific bug categories and complexity tiers. Together, these contributions span all four paper track categories — and both are grounded in the competition's provided graph and embedding dataset as explicitly encouraged.

The paper's claims are honest about their current standing: BCF is a proposed methodology with strong theoretical motivation and illustrative support, pending the controlled measurements described in Section 8. We believe the graph-first localization protocol is BCF's most transferable contribution — a concrete, reproducible method for using precomputed AST graphs and semantic embeddings to localize Python bugs, applicable to any future competition or deployment context that provides similar graph assets.
