Abstract
Autonomous coding agents operating on constrained hardware face a structural efficiency problem: without a principled reasoning methodology, agents waste the majority of their tool-call budget on unguided repository exploration rather than purposeful implementation. We introduce the Batonic Coding Framework (BCF), a specification-driven methodology that reframes autonomous software engineering as a four-phase disciplined process—issue specification, graph-guided localization, minimum-viable-patch generation, and validation-gated submission. Applied to the Google DeepMind/Kaggle Gemma 4 Developer Agent Competition, BCF reduces mean tool calls per resolved task by 62.5% on single-bug tasks (24 → 9 turns) and 66.7% on compound multi-root bugs (30 → 10 turns), while producing zero wrong edits in both cases. A key result is that BCF's advantage grows with task complexity: the methodology absorbs compound-bug ordering cost once, in Phase 1, whereas unstructured agents pay that cost repeatedly through wrong-edit recovery loops. BCF is implemented as a declarative Google ADK Agent Config with four reusable skill scripts, compatible with the competition harness without fine-tuning. All experiments run on consumer hardware (NVIDIA RTX 5090, 32 GB VRAM) with no cloud infrastructure.
Keywords: agentic software engineering · specification-driven development · AST call graphs · tool-call budget optimization · SWE-bench · Google ADK · Gemma 4

1Introduction

Autonomous software engineering has reached an inflection point. Frontier commercial systems achieve exceptional resolution rates on SWE-bench Verified—Claude Mythos Preview at 93.9%, GPT-5.6 Sol at 96.2%[1]—yet these systems rely on cloud-scale inference infrastructure unavailable to independent practitioners. The Google DeepMind and Kaggle Gemma 4 Developer Agent Competition constrains all participants to a single open-weight model, gemma-4-31b-it-qat-w4a16-ct, operating within a 50-turn budget per task and a 12-hour total evaluation window across approximately 120 held-out tasks.

Under these constraints, the primary axis of competition is not model capacity but agent methodology. Gemma 4 31B scores 86.4% on τ²-bench agentic tool use[2]—a single-generation leap from 6.6% for Gemma 3 27B—indicating strong multi-step tool-calling capability. Yet without specialized scaffolding, the same model achieves only 34–49% on SWE-bench Verified. The gap is not a model deficiency; it is a methodology gap. Existing coding agent approaches treat repository navigation as an unstructured exploration problem: the agent reads files and issues shell commands until it accumulates sufficient context, then attempts a fix. This approach wastes turns on exploration and produces agents that fix the most visible symptom before discovering the root cause.

We introduce the Batonic Coding Framework (BCF), a methodology that addresses both inefficiencies through structured, pre-implementation specification. BCF has been validated in applied product development—enabling a complete MVP to be built in 20 hours under live competition conditions with minimal rework—and now formalized for autonomous agentic software engineering. BCF's central claim is that a coding agent that writes an explicit solution specification before touching any file will consistently outperform an agent that explores and edits concurrently, regardless of the underlying model's raw capacity.

This paper makes four contributions: (1) BCF methodology—a four-phase framework for specification-driven autonomous software engineering, applicable through system prompting without fine-tuning; (2) graph-first localization—a structured tool-call sequence using AST call graphs and semantic embeddings to locate bug sites in 3–4 calls instead of 12–20 linear reads; (3) multi-bug scoping—a technique for identifying and ordering compound bug fixes before any file is read; and (4) empirical evaluation—full tool-call trace comparisons against an unstructured baseline on two tasks of increasing complexity.

2Background and Related Work

2.1 SWE-bench and the Competition Setting

SWE-bench[3] established the canonical benchmark for autonomous software engineering: given a natural-language GitHub issue and a frozen repository snapshot, an agent must produce a unified git diff resolving the issue such that the repository's own test suite passes. Each instance is evaluated as binary PASS/FAIL. The competition training corpus comprises 129 tasks from fastapi/fastapi, Textualize/rich, psf/requests, and encode/httpx. The hidden test set contains approximately 120 tasks from private repositories.

2.2 Gemma 4 31B as a Reasoning Foundation

The required model is a quantization-aware-trained (QAT) 4-bit variant of Gemma 4 31B. At INT4 quantization, inference requires approximately 18 GB VRAM—within consumer hardware limits. The model's τ²-bench agentic tool use score of 86.4%[2] demonstrates strong multi-step tool-calling capability. The gap between this score and SWE-bench Verified performance (34–49% without scaffolding) represents the methodology opportunity that BCF targets.

2.3 Prior Coding Agent Frameworks

SWE-agent[4] introduced the Agent-Computer Interface (ACI), providing structured file-system tools to reduce token overhead versus raw shell access. Aider[5] takes a conversational approach with developer guidance. CodeAct[6] and related frameworks extend agent action spaces to include code execution. None of these impose a pre-implementation specification requirement, which is BCF's primary structural departure.

2.4 The Budget Arithmetic

At 50 turns per task and 120 evaluation tasks, the theoretical maximum is 6,000 agent turns, subject to a 12-hour wall-clock cap. Agents averaging 27 turns per resolved task consume 3,240 turns—approaching the time budget when harder tasks and NO_PATCH outcomes are counted. Agents averaging 9.5 turns consume approximately 1,140 turns, leaving substantial reserve. Turn efficiency is not a performance metric; it is a structural determinant of how many tasks an agent can address within the evaluation window.

3The Batonic Coding Framework

BCF defines four sequential phases per task. Phases are strictly ordered: no file-access tool call may be issued before Phase 1 is complete; submit_patch() may not be called before Phase 4 validation passes. This sequencing is enforced through the multi-agent ADK configuration described in Section 4.

3.1 Phase 1: Specification Before Execution

Upon receiving a task, the BCF agent produces an explicit specification before issuing any file-access tool call. For each identified bug, the specification contains three mandatory fields: (a) Hypothesis—a declarative statement of probable root cause in code-level terms; (b) Target—the specific function or module most likely containing the defect; and (c) Fix shape—the minimum code transformation (delete, replace, guard-add) with estimated scope. For multi-bug issues, each bug receives its own triple, and fix order is determined by causal dependency: secondary bugs unreachable before the root cause is fixed must be ordered after it.

3.2 Phase 2: Graph-First Code Localization

BCF imposes a strict tool-call protocol for code exploration, prioritizing precomputed AST call graphs and 256-dimensional semantic embeddings over filesystem traversal:

Step 1: search_similar_code() — Two invocations with semantically distinct query phrases derived from the specification hypothesis.

Step 2: get_code_subgraph() — Applied to the top 3–5 symbols. Returns the structural call graph revealing candidate relationships.

Step 3: get_code_neighbors() — Applied to the most likely target symbol with edge_type: "called_by". Returns direct callers, which frequently contain the fix site.

Step 4: read_file() — With explicit line range derived from graph output. Never applied to an entire file.

run_command() with shell commands is not permitted for exploration in Phase 2. It is reserved exclusively for test execution in Phase 4. This constraint eliminates the most common source of wasted turns in unstructured agents: broad grep searches returning hundreds of matches with no structural ranking.

3.3 Phase 3: Minimum Viable Patch

The first edit_file() call implements exactly the specification's fix shape, derived from the targeted Phase 2 read. BCF prohibits exploratory edits—edits issued to observe test outcomes rather than to implement a specified change. For multi-bug tasks, patches are applied in root-cause-first order. Because the agent has already identified the exact string to replace (Phase 2) and what to replace it with (Phase 1), the edit is a transcription operation, not a discovery operation.

3.4 Phase 4: Validation-Gated Submission

BCF requires targeted run_command("pytest [specific files]") before submit_patch(). If validation fails, the agent re-reads the edited block (not the full file) and issues one corrective edit. A second failure triggers a budget-aware decision: if more than 20 turns remain, the code analyzer sub-agent escalates; if fewer, the best available patch is submitted. submit_patch() is never called on an unvalidated patch.

"A coding agent that knows what it's looking for before it starts looking will outperform one that looks until it finds something—every time, on every codebase."

4.2 BCF Skill Library

Four reusable skill scripts are included in submission/skills/ and invoked via run_skill_script(): spec_writer.py parses issue text into BCF specification format; graph_navigator.py orchestrates the two-query search → subgraph → neighbors sequence; context_assembler.py assembles minimum relevant code context as line-range tuples; and patch_validator.py runs targeted pytest and returns structured PASS/FAIL for Phase 4 diagnosis.

4.3 Hardware and Optional LoRA

All development was conducted on an NVIDIA RTX 5090 (32 GB GDDR7). The competition model requires approximately 18 GB VRAM for inference and 27 GB for QLoRA fine-tuning at 4-bit base—both within the 5090's capacity. The local inference server uses vLLM with --enable-auto-tool-choice and --tool-call-parser gemma required for structured tool call emission. An optional QLoRA adapter trained on successful task trajectories using Unsloth[10] is provided in submission/adapters/bcf_v1/ but is not required for the results reported here.

5Experimental Evaluation

5.1 Task Selection

Task A — fastapi_11194 (single-bug, single-file): A File upload parameter declared after a Form parameter causes 422 on valid multipart requests. Root cause: _merge_body_field_info() in fastapi/routing.py selects media_type from flat_body_fields[0], ignoring File-typed parameters declared later. Fix: 5-line replacement in one file.

Task B — httpx_6821 (two-bug, two-file): Redirect history is cleared on HTTP→HTTPS scheme upgrades; Response.stream raises AssertionError on history responses after the primary fix. Root cause 1: history.clear() in _send_handling_redirects. Root cause 2: hard assert self._stream is not None exposed as dead code once history is preserved. Fix: 2 deletions + 2 additions across two files.

5.2 Baseline Agent

The unstructured baseline uses the identical model, harness, and skill infrastructure with a generic system prompt instructing the agent to read the issue, explore the codebase, and submit a correct fix. The baseline is not restricted from using graph tools but applies no specification discipline. It represents a capable but unstructured agent—not a random walker.

5.3 Metrics

We report five per-task metrics: (1) total turns consumed; (2) wrong edits—edit_file() calls absent from the final submitted diff; (3) fix-order error—whether a secondary bug was addressed before its root cause; (4) exploration turns—tool calls consumed before the first correct edit; and (5) budget remaining at submission out of 50.

6.1 Turn Efficiency

BCF consumed 9 turns for Task A and 10 for Task B, compared to 24 and 30 for the baseline. The exploration phase accounts for the majority of savings: BCF's Phase 2 protocol located the bug site in 4 tool calls on both tasks, while the baseline required 12–16 calls of grep, whole-file reads, and repeated linear searches. The remaining gap is attributable to wrong-edit recovery—the baseline produced 3 wrong edits per task, each consuming 2 recovery turns (re-read plus corrective edit), totaling 6 lost turns per task.

6.2 Fix-Order Correctness on Compound Tasks

On Task B, the baseline fixed the secondary symptom—the AssertionError in Response.stream—before discovering the root cause, because the secondary error appeared first in pytest output. The baseline spent turns 3–8 on the secondary fix, then consumed turns 9–22 locating the root cause. BCF's Phase 1 specification identified both bugs from the issue description before any file was read, determined fix order by causal dependency (root cause first), and executed accordingly. BCF resolved Task B in 10 turns with zero wrong edits versus 30 turns and 3 wrong edits for the baseline.

6.3 Projected Budget Utilization at Scale

Projected across the 120-task hidden evaluation set, BCF's mean of 9.5 turns per task yields approximately 1,140 total turns—19% of the 6,000-turn theoretical cap—leaving substantial reserve for harder tasks. The baseline's mean of 27 turns yields approximately 3,240 turns, approaching the time budget when NO_PATCH outcomes and unsolved tasks are counted. This reserve capacity is the competition-level implication of per-task efficiency: more tasks are addressable within the same evaluation window.

7Discussion

7.1 Why Specification-First Works

The primary mechanism of BCF's efficiency is constraint propagation. A concrete hypothesis about bug location produces one targeted read_file() call rather than five speculative reads. An explicit list of bugs with fix-order constraints prevents secondary-before-root ordering errors. These are structural guarantees imposed by Phase 1's existence as a mandatory first step, not heuristic improvements. The analogy in human engineering is direct: specification-before-implementation reduces rework by catching design errors upstream, and this principle applies to autonomous agents with equal or greater force—agents cannot recover cheaply from wrong edits.

7.2 Superlinear Advantage on Compound Tasks

BCF's efficiency advantage grew from 62.5% on the single-bug task to 66.7% on the compound task, despite the compound task being harder. This is consistent with the hypothesis that BCF's advantage is superlinear in task complexity. Single-bug tasks offer fewer opportunities for wrong-order fixing. As tasks include multiple causally-dependent bugs and misleading symptoms, unstructured agents accumulate wrong edits multiplicatively, while BCF's specification phase absorbs the compound complexity once—at Phase 1 entry.

7.3 Methodology as Durable Differentiation

Because BCF is a methodology rather than a model architecture, it provides competitive differentiation not visible from a leaderboard position. A competitor observing a BCF submission's ADK configuration gains no insight into the Phase 1 specification discipline, the two-query graph-first protocol, or the budget-aware Phase 4 decision logic. BCF's value is embedded in prompting, skill scripts, and structural sub-agent boundaries—not in the external submission format. More broadly, BCF represents a practitioner contribution: a framework that any developer can adopt without ML expertise, on consumer hardware, achieving competitive outcomes through disciplined reasoning rather than compute scale.

7.4 Limitations and Future Work

BCF's Phase 1 specification quality depends on issue description completeness. Vague reports produce weak hypotheses, which produce less precise Phase 2 search queries. Future work will explore retrieval-augmented specification: grounding hypotheses in similar resolved issues from the training corpus. The current evaluation covers two tasks from the training corpus; a full-scale evaluation across all 129 training tasks would strengthen the quantitative claims. The optional QLoRA adapter is not evaluated here; ablation results for trajectory-trained fine-tuning will be released separately.

8Conclusion

The Batonic Coding Framework demonstrates that a structured, specification-driven methodology substantially improves autonomous software engineering agent efficiency without changes to the underlying model. By requiring agents to specify before they explore and to localize before they edit, BCF reduces mean tool calls per resolved task by 62.5–66.7% while eliminating wrong-edit recovery overhead entirely. The compounding advantage on compound multi-root tasks—where specification correctly orders fixes that unstructured agents discover in the wrong sequence—indicates that BCF's benefits scale with task complexity.

BCF is implemented as a declarative Google ADK Agent Config with four reusable skill scripts, compatible with the competition harness and developed entirely on consumer hardware without cloud infrastructure. We submit BCF as a new application of principled software engineering methodology to the autonomous agent domain, with the expectation that its core principles—specification first, graph-guided localization, minimum viable patch—will generalize to any agentic software engineering context where tool-call budgets and task complexity make unstructured exploration costly.

We hope this work contributes to a broader shift in how the field thinks about coding agent improvement: not only through better models, but through better structured reasoning habits that any model can adopt.
