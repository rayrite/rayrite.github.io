## 2. Anatomy of a headless invocation

Usage template: `blender [args ...] [file] [args ...]` [confirmed: https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html (mirror: https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/advanced/command_line/arguments.rst)]. The single most important automation fact is the **argument-order rule**: “Arguments are executed in the order they are given,” and the docs give the trio of examples showing that `-o`/`-F` must be set **after** the blend file loads and **before** `-f`/`-a` run [confirmed: same arguments page, “Argument Order” section; repeated as a note + “Always position `-f` or `-a` as the last arguments” on the render page, https://docs.blender.org/manual/en/latest/advanced/command_line/render.html — mirror: https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/advanced/command_line/render.rst]. Arguments must be space-separated (`-ba` is an unknown argument and Blender exits) and are case-sensitive (`-F` ≠ `-f`) [confirmed: both mirrors].

Canonical render examples (straight from the official render page):
```sh
blender -b file.blend -f 10                                  # one still
blender -b file.blend -o /project/renders/frame_##### -F OPEN_EXR -f -2   # 2nd-to-last frame, 5-digit padding
blender -b file.blend -a                                     # whole animation, blend settings
blender -b file.blend -E CYCLES -s 10 -e 500 -t 2 -a         # engine, frame range, 2 threads
```
[confirmed: https://docs.blender.org/manual/en/latest/advanced/command_line/render.html — mirror above]

> Note on the task’s cited URL `…/render/workflows/command_line.html`: that section was reorganized — the 4.x/5.x manual tree contains **no `render/workflows` directory**; the command-line rendering content lives at `advanced/command_line/render.html` [confirmed: file listing via https://projects.blender.org/api/v1/repos/blender/blender-manual/git/trees/blender-v4.5-release?recursive=true and ?recursive=true on `main`; the 3.6-era archive URL https://docs.blender.org/manual/en/3.6/render/workflows/command_line.html is [inferred] as the historical location].

## 3. Core flag table (all verified in the arguments page; identical between the 4.5-LTS and 5.x builds)

| Flag | Long form | Meaning (condensed from docs) |
|---|---|---|
| `-b` | `--background` | UI-less mode; **audio device disabled by default**, re-enable with `-setaudio Default` after the flag |
| `-a` | `--render-anim` | Render frames start→end (inclusive) |
| `-S <name>` | `--scene` | Set active scene for rendering |
| `-f <frame>` | `--render-frame` | Render and save one frame; `+n`/`-n` are relative to start/end; comma lists (no spaces) and `1..10` ranges accepted |
| `-s/-e <frame>` | `--frame-start/--frame-end` | Frame range (relative `+/-` allowed) |
| `-j <n>` | `--frame-jump` | Step size between rendered frames |
| `-o <path>` | `--render-output` | Output path; `//` prefix = relative to the blend file; path templating (`{blend_name}`); `#` = zero-padded frame number; if the name has no `#`, `####` is appended |
| `-E <engine>` | `--engine` | Render engine; `-E help` lists available engines |
| `-t <n>` | `--threads` | 1–1024, `0` = all CPU cores |
| `-F <fmt>` | `--render-format` | `TGA RAWTGA JPEG IRIS PNG BMP HDR TIFF` (+ system-dependent `OPEN_EXR`, `OPEN_EXR_MULTILAYER`, `FFMPEG`, `CINEON`, `DPX`, `JP2`, `WEBP`) |
| `-x <bool>` | `--use-extension` | Append file extension to output — **this is what `-x` means; it is *not* `--threads`** (the task brief had these conflated) |
| `--` | — | Stop Blender’s option parsing; following args go to Python via `sys.argv` |
| `-h` / `-v` | `--help` / `--version` | Print help / version and exit |
| `-c <cmd>` | `--command` | Run a built-in command consuming all remaining args; implies `--background`. Commands on 5.2: `asset_listing`, `extension`, `maketx` (`-c help` lists) |

[confirmed: https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html — mirror https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/advanced/command_line/arguments.rst; the `-c` command list **ran: 5.2.2**]

Cycles options must appear **after a second `--`**: `--cycles-device <CPU|CUDA|OPTIX|HIP|ONEAPI|METAL>` (append `+CPU` for hybrid; example `blender -b file.blend -f 20 -- --cycles-device OPTIX`) and `--cycles-print-stats` [confirmed: arguments mirror, “Cycles Render Options”]. Other useful automation flags: `--factory-startup` (skip user `startup.blend`), `-y/--enable-autoexec` vs `-Y/--disable-autoexec` (default disabled), `--addons <a,b>` (comma list, no spaces, enable add-ons), `--online-mode/--offline-mode` (override internet-access preference), `--python-exit-code <0..255>` (exit code if a command-line Python script raises), `--python-use-system-env` (honors `PYTHONPATH`/user site-packages), `-noaudio`/`-setaudio <None|Default|SDL|OpenAL|CoreAudio|JACK|PulseAudio|WASAPI>` [confirmed: arguments mirror]. Version note: 5.x added Windows `--qos` and `--gpu-vsync`, `--log-list-categories`, `BLENDER_OCIO` env var, and dropped `AVIRAW/AVIJPEG` from `-F`; none change the core pipeline [confirmed: diff of `blender-v4.5-release` vs `main` copies of arguments.rst].

Environment knobs for build farms: `BLENDER_USER_RESOURCES`/`BLENDER_USER_CONFIG`/`BLENDER_USER_SCRIPTS`/`BLENDER_USER_EXTENSIONS`/`BLENDER_USER_DATAFILES` and `BLENDER_SYSTEM_*` equivalents [confirmed: arguments mirror, “Environment Variables”].

## 4. `bpy` essentials for pipeline scripts

Embedding flags: `-P <file>` / `--python <file>` runs a script file; `--python-expr <expression>` runs an inline script (“may be a complete multi-line script; you are limited only by the platform’s maximum argument length”); `--python-console` starts a REPL; `--python-text <name>` runs a text block stored in the blend [confirmed: arguments mirror].

Operators used in every automation script (all verified in official source/templates):
- `bpy.ops.wm.read_factory_settings(use_empty=True)` — reset to an empty scene; the API doc and the official `background_job.py` template both use this to clear state; the `bpy` pip-module behaves “as if `--factory-startup`” and needs it to avoid the default cube [confirmed: https://docs.blender.org/api/current/info_advanced_blender_as_bpy.html — mirror https://raw.githubusercontent.com/blender/blender/blender-v4.5-release/doc/python_api/rst/info_advanced_blender_as_bpy.rst; and https://projects.blender.org/blender/blender/raw/branch/blender-v4.5-release/scripts/templates_py/background_job.py; **ran: 5.2.2**].
- `bpy.ops.wm.read_homefile()` / `bpy.ops.wm.read_userpref()` [confirmed: same API mirror; C-level `WM_OT_read_homefile` in `source/blender/windowmanager/intern/wm_files.cc`].
- `bpy.ops.wm.save_as_mainfile(filepath=…)` (also `save_mainfile`) [confirmed: background_job template; `WM_OT_save_as_mainfile` in `wm_files.cc`].
- `bpy.ops.render.render(write_still=True)` plus `scene.render.filepath`, `scene.render.use_file_extension` for in-script renders [confirmed: background_job template].
- Scene control from Python: `scene = bpy.context.scene`; set `scene.render.engine = 'CYCLES'` (or the 4.x `'BLENDER_EEVEE_NEXT'` / 5.x `'BLENDER_EEVEE'`) and `scene.frame_set(n)` [inferred from engine constants verified in `scene.cc` + standard RNA; the engine strings themselves are confirmed as above].
- Pass custom args after `--` and read them from `sys.argv` (the template’s usage line: `blender --background --factory-startup --python $HOME/background_job.py -- --text="Hello World" --render="/tmp/hello" --save="/tmp/hello.blend"`) [confirmed: https://projects.blender.org/blender/blender/raw/branch/blender-v4.5-release/scripts/templates_py/background_job.py].

`bpy` as a standalone Python module: official docs describe it, note **a precompiled `bpy` wheel is published on PyPI (`pip install bpy`)**, and that CLI-only settings like `--threads`/`--log` have no API equivalent [confirmed: API mirror above; https://pypi.org/project/bpy/]. For CI-style conversion jobs the classic `-b file.blend -P script.py` form remains the most robust path [inferred; consistent with all sources above].

## 6. Full verified example — load a `.blend` and export for Unity

Save as `export_for_unity.py`; run headless against a blend. This exact pair (generator + exporter) was executed successfully on Blender 5.2.2 LTS, producing `unity_export.glb`, `unity_sep.gltf` (+`.bin`), `unity_export.fbx`, `unity_obj.obj`+`.mtl` [ran: 5.2.2].

```python
# export_for_unity.py — usage:
#   blender -b test_stack.blend --python export_for_unity.py
import bpy

scene = bpy.context.scene
print("LOADED:", bpy.data.filepath)

# glTF binary for Unity glTF importer (Y-up per spec, apply modifiers)
bpy.ops.export_scene.gltf(filepath="unity_export.glb", export_format="GLB",
                          use_selection=False, export_apply=True, export_yup=True)

# glTF separate for human-readable inspection
bpy.ops.export_scene.gltf(filepath="unity_sep.gltf", export_format="GLTF_SEPARATE")

# FBX for Unity's native importer (no armatures here; leaf-bones off)
bpy.ops.export_scene.fbx(filepath="unity_export.fbx",
                         object_types={'MESH', 'CAMERA', 'EMPTY'},
                         apply_scale_options='FBX_SCALE_ALL',
                         path_mode='COPY', add_leaf_bones=False)

# Wavefront (5.x native operator) — note: no armatures/cameras/lights [confirmed:
# https://docs.blender.org/manual/en/4.5/files/import_export/obj.html]
try:
    bpy.ops.wm.obj_export(filepath="unity_obj")
except AttributeError:
    print("OBJ_UNAVAILABLE (pre-5.x: enable the legacy io_mesh_obj extension)")

print("EXPORT DONE")
```

Generator side (creating a `.blend` headless) follows the official `background_job.py` pattern: `bpy.ops.wm.read_factory_settings(use_empty=True)` → link objects via `bpy.data.*.new(...)` + `scene.collection.objects.link(ob)` → `bpy.ops.wm.save_as_mainfile(filepath=...)` → for a still: `bpy.ops.render.render(write_still=True)` with `scene.render.filepath` and `scene.render.use_file_extension = True` [confirmed: https://projects.blender.org/blender/blender/raw/branch/blender-v4.5-release/scripts/templates_py/background_job.py; **ran: 5.2.2**].

Batch one-liners for a preview-render farm (note flag order — engine/output before `-a`, range via `-s/-e`, and `//` blend-relative outputs; plain relative paths like `-o render_` may resolve against the process CWD — use absolute paths from scripts [ran: 5.2.2, observed `C:\render_0001.png` attempt from a bare relative `-o`]):

```bat
"blender.exe" -b stack.blend -E BLENDER_WORKBENCH -o "D:\out\prev_####" -F PNG -x 1 -s 1 -e 2 -a
"blender.exe" -b stack.blend -E CYCLES -f 1 -- --cycles-device CPU
"blender.exe" -b --factory-startup --python-exit-code 42 -P script_that_must_not_throw.py
```

## 7. Gotchas & quick-reference version deltas

1. **Order kills pipelines:** `-o`/`-F`/`-x` before `-a`/`-f`, and the blend file before the settings it must not clobber [confirmed: arguments mirror “Argument Order”].
2. **`-b` disables audio by default** — matters for sequenced exports that read VMD/sound drivers: add `-setaudio Default` [confirmed: arguments mirror].
3. **Auto-exec security:** scripts/drivers in `.blend` files do not run unless `-y`/`--enable-autoexec` is passed; conversely, untrusted blends stay inert by default [confirmed: arguments mirror `-Y … (default)`].
4. **Engine strings:** 4.5 LTS → `-E BLENDER_EEVEE_NEXT` / scene default `BLENDER_EEVEE_NEXT`; 5.x → `-E BLENDER_EEVEE` is the EEVEE (Next) engine, `BLENDER_EEVEE_NEXT` silently mapped for compatibility; both still have `CYCLES` and `BLENDER_WORKBENCH` [confirmed: scene.cc 4.5/5.0 mirrors + creator_args.cc main; **ran: 5.2.2**].
5. **Operator renames:** glTF/FBX stay `bpy.ops.export_scene.{gltf,fbx}` across 4.x→5.x (still `dir()`-visible in 5.2 [ran: 5.2.2]); OBJ moved `export_scene.obj` (legacy add-on, [unverified exact id]) → `wm.obj_export/wm.obj_import` (4.x extension, 5.x native C++) [confirmed: 4.5 manual anchor; 5.x `io_obj.cc`; **ran: 5.2.2**].
6. **Deprecated API:** `Material.use_nodes` warns on 5.2, removed by 6.0 — new editor/tooling scripts should rely on node materials being the default [ran: 5.2.2].
7. Headless needs **no display server** on Linux (the official render page highlights the SSH/remote use case) [confirmed: https://docs.blender.org/manual/en/latest/advanced/command_line/render.html].
8. For fully scripted farms, the `bpy` PyPI wheel exists but lacks CLI-only controls (`--threads`, `--log`) — prefer real Blender + `-P` for render/convert jobs [confirmed: info_advanced_blender_as_bpy mirror + https://pypi.org/project/bpy/].

## 7. Architecture: addon-side TCP socket bridged to a stdio MCP server

The MCP side uses **stdio**: per the spec, "The client launches the MCP server as a subprocess. The server reads JSON-RPC messages from its standard input (`stdin`) and sends messages to its standard output (`stdout`)," newline-delimited; Streamable HTTP is the other standard transport [confirmed: https://modelcontextprotocol.io/specification/2025-06-18/basic/transports].

The Blender side is **not** MCP. It is "a simple JSON-based protocol over TCP sockets" [confirmed: https://raw.githubusercontent.com/ahujasid/blender-mcp/main/README.md]:

- Defaults: `DEFAULT_HOST = "localhost"`, `DEFAULT_PORT = 9876`; env vars `BLENDER_HOST`, `BLENDER_PORT`; precedence CLI flags (`--host`, `--port`) > env > defaults; `ADDON_PROTOCOL_VERSION = 9` handshake via `get_addon_status` version check [confirmed: https://raw.githubusercontent.com/ahujasid/blender-mcp/main/src/blender_mcp/server.py and .../addon.py].
- Server→addon messages are JSON of the form `{"type": "<command_type>", "params": {...}}` sent with `sendall`; responses are reassembled in 8192-byte chunks with repeated `json.loads` attempts and a 180 s socket timeout; `"status": "error"` raises with the message [confirmed: https://raw.githubusercontent.com/ahujasid/blender-mcp/main/src/blender_mcp/server.py].
- Addon threading model: a server thread `_server_loop` accepts connections; per-client daemon threads `recv(8192)` and push parsed commands into `self.command_queue`; a main-thread consumer registered with `bpy.app.timers.register(..., persistent=True)` drains the queue every 0.05 s because "bpy.app.timers is not thread-safe" — so all `bpy` execution happens on Blender's UI thread [confirmed: https://raw.githubusercontent.com/ahujasid/blender-mcp/main/addon.py].
- Security: the socket has "no authentication or encryption"; anyone reaching the port can run Python in Blender — keep it on localhost, prefer an SSH tunnel remotely; optional `BLENDER_MCP_SAFE_MODE=1` validates/blocks risky scripts (file I/O, running programs, network, persistent code); telemetry is opt-in for content, minimal anonymous usage stats can be disabled with `DISABLE_TELEMETRY=true` [confirmed: https://raw.githubusercontent.com/ahujasid/blender-mcp/main/README.md].

## 8. How this differs from Unity's MCP (official `com.unity.ai.assistant`)

Unity's official MCP bridge, per docs.unity3d.com [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.7/manual/integration/unity-mcp-overview.html]:

- The in-editor component is the **MCP Bridge**; it "launches automatically" at Unity startup and opens a local **IPC channel — named pipes on Windows, Unix sockets on macOS/Linux** (BlenderMCP instead uses a plain TCP socket on 9876).
- External clients never talk to the Editor directly: a separate **relay binary** installs to `~/.unity/relay/` and "runs as an MCP server process that AI clients start." Client→relay is **stdio MCP**; relay→Editor is the IPC pipe (BlenderMCP collapses both hops into one Python process that speaks MCP on stdio and TCP to the addon).
- Config path `Edit > Project Settings > AI > Unity MCP`; connections from **AI Gateway** are auto-approved while **direct** MCP client connections require in-editor user approval, with remembered grants (BlenderMCP has *no* approval layer at all — just an unauthenticated localhost socket).
- Built-in Unity tool categories: "scene management, asset operations, script editing, and console access"; custom tools register via attributes (e.g., `[McpTool]`); multiple simultaneous clients supported (BlenderMCP: one server instance, single shared socket queue).
- 2026 transition: "Unity has deprecated the MCP server included in the in-editor AI assistant package. The Unity CLI replaces this MCP server" via `unity mcp` ("MCP mode ... remains fully supported"; migrate with `unity pipeline install`, then `unity mcp configure <client>`; "To drive a running Editor through the Unity Pipeline package, use Unity 6.0 LTS or later"; "Third-party MCP packages from GitHub that you installed to get agent access into Unity are unaffected") [confirmed: https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli]. Community/third-party Unity MCPs like CoplayDev/unity-mcp therefore remain valid parallels to BlenderMCP's third-party status [confirmed: https://github.com/CoplayDev/unity-mcp].

**Architectural verdict:** both ecosystems converge on the same pattern — *an in-DCC-tool server process bridged to an MCP client over a local channel* — but differ in trust and lifecycle: Unity (official) = auto-started bridge, OS-level IPC, explicit client approval, curated tool taxonomy + extensibility; BlenderMCP = manual "Connect" button, raw TCP JSON protocol with zero authentication, arbitrary-code-execution as the primary primitive. For our pipeline this means BlenderMCP gives faster iteration (full `bpy` access, asset stores, GLB/FBX export for Unity import) while Unity-side automation should follow Unity's first-party MCP/CLI guidance. [inferred: the comparative risk/lifecycle framing is analysis over the cited facts, not a documented claim.]

- Universal ("Intel 64-bit + Apple silicon") builds are larger than per-arch builds [confirmed: same URL].
- Plan: **Apple silicon (ARM64) primary**; universal build only if we commit to Intel support for launch window [inferred].

**Code signing (Unity's own documentation of Apple's process):**
- Unity "adds a code signature to every macOS build it produces" (a default signing identity); notarization requires a real **Developer ID** signature [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/macoscodesigning.html, https://docs.unity3d.com/6000.1/Documentation/Manual/macoscodesigning.html (same content family)].
- Workflow steps documented: create Developer ID Application certificate (`.cer`) on the Apple portal → add to Keychain (shows as "Developer ID Application : XXX (YYY)") → chmod, then sign with the quoted flag set: `codesign --deep --force --verify --verbose --timestamp --options runtime --entitlements "application_name.entitlements" --sign "Developer ID Application : XXX (YYY)" "application_name.app"` (preceded by `chmod -R a+xr "application_name.app"`) [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/macoscodesigning.html].
- **Hardened Runtime minimum entitlements** per Unity's page: `com.apple.security.cs.disable-library-validation` and `com.apple.security.cs.disable-executable-page-protection`, both `<true/>` — these are exactly what an engine bundling dylibs/JIT-ish runtime needs [confirmed: same URL].
- Notarization hub lists two documented paths for 6000.6: "Notarize with Xcode and command-line tools" and "Notarize with altool" (legacy) [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/macos-building-notarization.html].
- Xcode/CLI page exact prerequisites + commands: Apple ID, macOS 10.15+, **Xcode 11+**, Apple Developer Program membership, app-specific password (`xxxx-xxxx-xxxx-xxxx`); package with `ditto -c -k --sequesterRsrc --keepParent "application_name.app" "application_name.zip"`; after success, staple with `xcrun stapler staple "ApplicationName.app"` [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/macosnotarizationxcode.html].
- Apple side: the canonical policy page is "Notarizing macOS software before distribution" (Gatekeeper blocks/flags un-notarized Developer ID apps distributed outside the Mac App Store; notarization ≠ App Review) [confirmed: https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution — page body is JS-rendered so exact prose could not be scraped; treat flag-level Apple details as corroborated by Unity's pages above].
- Steamworks.NET caveat that directly hits this pipeline: a stray `Steamworks.NET.txt` file breaks **Unity Cloud Build notarization** [confirmed: https://github.com/rlabrecque/Steamworks.NET/issues/397].

## 4. Steam — Steamworks SDK, app pipeline, features

**Access & SDK.** Steamworks docs are public at partner.steamgames.com/doc/home, but SDK download requires a Steamworks partner account at the download list; **the SDK is "only required to upload your content to Steam"** — its APIs (achievements, overlay, etc.) are optional integrations [confirmed: https://partner.steamgames.com/doc/home, https://partner.steamgames.com/doc/sdk]. SDK ships `public/steam`, `redistributable_bin`, `tools/ContentBuilder` (incl. `builder/builder_linux/builder_osx` `steamcmd.exe`), SpaceWar example [confirmed: https://partner.steamgames.com/doc/sdk].

**App setup pipeline (docs-confirmed):** create the app in Steamworks → App ID issued; upload builds with ContentBuilder; set a build **live on a branch** in App Admin (default branch cannot be auto-set-live from the script: "can not set the build live on the default branch automatically"; released-app promotion needs phone-verified account + 3-day security wait) [confirmed: https://partner.steamgames.com/doc/store/application/branches, https://partner.steamgames.com/doc/sdk/uploading]. Steam Direct onboarding is "fill out some digital paperwork, pay a small per-app fee" (exact fee figure lives behind the partner portal) [confirmed: https://partner.steamgames.com/quickstart; fee amount: inferred/omitted].
- **Depots** = "a logical grouping of files which are all delivered to a customer as a single group"; mount rules by Language, OS, Architecture (for 32/64 splits), DLC; shared depots from a master app; OS store data must match a mountable depot per OS [confirmed: https://partner.steamgames.com/doc/store/application/depots]. Practical layout: one depot per OS (Win64 / macOS / Linux-optional) [inferred].
- **Branches** ("Betas"): default branch is what customers get; players switch under Properties → Game Versions & Betas [confirmed: https://partner.steamgames.com/doc/store/application/branches].
- **Upload mechanics (exact):** app script `app_build_<AppID>.vdf` with `AppID/Desc/ContentRoot/BuildOutput/Depots` and optional `Preview`, `Local`, `SetLive <branch>`; depot script `depot_build_<DepotID>.vdf` with `FileMapping` (`LocalPath`,`DepotPath`,`Recursive`), `FileExclusion`, `InstallScript`, `FileProperties` (`userconfig`/`versionedconfig`); run via `tools\ContentBuilder\builder\steamcmd.exe +login <account> <password> +run_app_build ..\scripts\simple_app_build.vdf +quit`; CI login-token reuse by preserving `config.vdf` after an interactive `+login <username>` [confirmed: https://partner.steamgames.com/doc/sdk/uploading].

**Features we'd integrate:**
- **Achievements:** configured in App Admin (API Name, ID, Progress Stat tie-in, Set By, Hidden flag, achieved/unachieved icons); launch cap "games are limited to 100 achievements at first"; code side `ISteamUserStats::SetAchievement` + `StoreStats`, `UserAchievementStored_t` / `UserStatsStored_t` callbacks, `IndicateAchievementProgress`, localization delivered automatically per client language; icons/names "all-ages appropriate" [confirmed: https://partner.steamgames.com/doc/features/achievements].
- **Steam Cloud:** two paths — **Auto-Cloud** (no code: file groups with Root/Subdirectory/Pattern/OS/Recursive paths, syncs "when the application launches and exits") or **ISteamRemoteStorage** API (more control; 100 MB per `FileWrite`/`FileWriteStreamWriteChunk` call max, 256 MB manifest warning); quota per user per game set on the Steam Cloud Settings page (`Byte quota per user`, `Number of files allowed per user`) — must Save **and Publish**; debug via `%Steam Install%\logs\cloud_log.txt` [confirmed: https://partner.steamgames.com/doc/features/cloud]. For our save-game: Auto-Cloud with a pattern over `user://` writes is the cheapest route [inferred].
- **Overlay:** activates over games with SHIFT+TAB default; supported APIs incl. DirectX 7–12, OpenGL, Metal, Vulkan; call `SteamAPI_Init` "before creating the OpenGL/D3D device so the overlay can hook device creation"; handle `GameOverlayActivated_t` to pause/resume; `ISteamFriends::ActivateGameOverlayToStore/ToWebPage/ToUser`, `ISteamUtils::SetOverlayNotificationPosition` [confirmed: https://partner.steamgames.com/doc/features/overlay].
- **API lifecycle:** `SteamAPI_Init` "MUST be called and return successfully prior to accessing any of the Steamworks Interfaces"; `SteamAPI_RestartAppIfNecessary` relaunches games not launched through Steam, "if a `steam_appid.txt` file is present then this will return false regardless"; `SteamAPI_RunCallbacks` "Most games call this once per render-frame" [confirmed: https://partner.steamgames.com/doc/sdk/api]. `steam_appid.txt` = text file "next to your executable containing just the App ID and nothing else", dev-only ("do not ship") [confirmed: https://partner.steamgames.com/doc/sdk/api; also https://partner.steamgames.com/doc/sdk/api/example].

**Steam Input vs Unity Input System gamepads (the key architectural question):**
- **Emulation path (zero Unity changes):** on Windows the overlay "hook[s] traditional gamepad input APIs such as XInput, DirectInput, RawInput, and Windows.Gaming.Input" and "inject[s] an emulated Xbox controller device"; on macOS/Linux emulation comes from a driver; "The controller will show up in your game as an Xbox controller" [confirmed: https://partner.steamgames.com/doc/features/steam_controller/steam_input_gamepad_emulation_bestpractices]. Unity's Input System therefore sees an `XInputController` and standard bindings just work [confirmed: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.15/manual/Gamepad.html]. Valve's config guidance: enable Steam Input by "checking all checkboxes other than Xbox" in app admin; note the collision example (PlayStation trackpad/options both map to XInput Start) and that gyro-as-mouse only works for single local player under emulation [confirmed: https://partner.steamgames.com/doc/features/steam_controller/steam_input_gamepad_emulation_bestpractices].
- **Steam Input API path (`ISteamInput`):** for correct glyphs/origin translation call `Init`+`RunFrame`, then `GetControllerForGamepadIndex`, `GetActionOriginFromXboxOrigin`, `GetGlyphForActionOrigin`, `TranslateActionOrigin`; API-managed pads won't appear in emulation slot lookups; "If you're interested in future-proof glyph support please integrate Steam Input API" [confirmed: same URL]. On-screen keyboard via `ISteamUtils::ShowGamepadTextInput` family [confirmed: same URL].
- **Unity-side facts:** Input System models gamepads as `Gamepad` with standard-layout controls (`leftStick`, `rightStick`, `dpad`, `buttonNorth/South/East/West`, `leftTrigger`, `startButton`...); explicit device support classes include `XInputController`, `DualShock4GamepadHID`, `DualSenseGamepadHID`, `SwitchProControllerHID`; unrecognized HID gamepads surface as generic joysticks, not `Gamepad`; `VirtualMouseInput` drives the cursor from a gamepad [confirmed: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.15/manual/Gamepad.html]. The package's @latest docs are now versioned in Unity-6 style (e.g. "Input System | 6.7.0") while 1.14/1.15 pages remain for the 6000.x bundles — resolve the version actually bundled with 6000.6 in the project's `Packages/manifest.json` [confirmed: https://docs.unity3d.com/Packages/com.unity.inputsystem@latest/; exact-bundled-version: inferred].
- **Recommended posture:** play local-first: bind the **Unity Input System Standard Gamepad** layout (works for Xbox pads, Steam-emulated pads, native DualSense), keep a thin `ISteamInput` adapter only for glyph rendering and Steam Deck ergonomics; Steam Input handles remaps so we never ship our own binding UI as the source of truth on Steam [inferred from the two confirmed docs].

```csharp
        if (report.summary.platform != BuildTarget.StandaloneWindows64 &&
            report.summary.platform != BuildTarget.StandaloneOSXARM64) return; // enum names: verify in 6000.6 ScriptReference [inferred]
```

## 1. iOS build configuration

### 1.1 Scripting backend, architecture, graphics

- **IL2CPP is the only scripting backend offered for iOS** — the Unity 6.6 iOS Player settings page lists "Scripting Backend" with only IL2CPP; no Mono option is shown. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsiOS.html]
- IL2CPP compiles C# ahead-of-time (AOT) to C++ and is the backend required to ship 64-bit iOS binaries to the App Store. [confirmed: https://docs.unity3d.com/6000.5/Documentation/Manual/il2cpp-introduction.html — excerpt states IL2CPP "is the only scripting backend that supports deploying to ARM 64-bit on iOS, and is therefore mandatory for releasing new apps to the Apple App Store"]
- **Architecture: "Only ARM64 is available for iOS."** The same Player settings page lists a separate **Simulator Architecture** with options "ARM64", "X86_64 (Deprecated)", "Universal (Deprecated)". [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsiOS.html]
- **Graphics API: Metal.** "iOS devices support Metal" and no other graphics API is listed; the iOS Player settings page exposes only Metal-specific toggles ("Metal API Validation", "Metal Write-Only Backbuffer", "Force hard shadows on Metal"). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/ios-requirements-and-compatibility.html and [inferred] Metal-only conclusion from absence of GLES options on the Player settings page]
- Texture formats: DXT unsupported on iOS; ASTC, ETC2, ETC natively supported. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/ios-requirements-and-compatibility.html]
- **API compatibility level** options on iOS in 6000.6: ".Net Framework" and ".Net Standard 2.1" (the latter "Produces smaller builds and has full cross-platform support"). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsiOS.html]

### 1.2 OS versions and Xcode requirements

- **Unity 6.6 supports iOS 15 and above**: "Unity supports iOS 15 and above." [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/ios-requirements-and-compatibility.html]
- Version-stream difference to note: the Unity **6000.0** page for the same topic stated iOS 13+ and recommended "Xcode 15+"; by **6000.6** the floor is iOS 15 and the recommendation is **Xcode 16 or later**. [confirmed via search excerpt: https://docs.unity3d.com/6000.0/Documentation/Manual/ios-requirements-and-compatibility.html; confirmed (6.6 values): https://docs.unity3d.com/6000.6/Documentation/Manual/ios-requirements-and-compatibility.html]
- Unity's system-requirements page for 6.6 repeats the hard floor: **"Xcode version 16 or later"** for iOS/iPadOS build support, and defers store submission floors to Apple: "refer to Apple's submission guidelines for the required Xcode version." [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/system-requirements.html]
- **Apple's submission floor is higher than Unity's editor floor**: "Since April 28, 2026 — Apps uploaded to App Store Connect must be built with Xcode 26 or later using an SDK for iOS 26, iPadOS 26, tvOS 26, visionOS 26, or watchOS 26." [confirmed: https://developer.apple.com/news/upcoming-requirements/] → [inferred] For any store-bound 6.6 build, the build Mac must run **Xcode 26.x** (Unity's Xcode 16 floor only guarantees editor compatibility); [inferred] Apple raises this minimum-SDK floor annually, so re-check the "Upcoming Requirements" page at submission time.
- The Unity Editor on macOS itself requires macOS Ventura 13 or newer. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/system-requirements.html]
- Building for iOS locally requires macOS (Xcode is Apple-only); alternatively Unity Build Automation can build in the cloud. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/ios-environment-setup.html — "Xcode is only available for macOS"; the iOS Build Support module is required]
- A **free Apple ID** suffices to build-and-test on your own device; the **paid Apple Developer Program** is required for distribution and services (Game Center, IAP). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/ios-environment-setup.html]

### 1.3 Build process and generated Xcode project structure

- The pipeline "has two main steps": Unity **generates an Xcode project**, then **Xcode compiles and signs** it. "You need to build and sign this project before you deploy it on a device or distribute it on the App Store." [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html and https://docs.unity3d.com/6000.6/Documentation/Manual/StructureOfXcodeProject.html]
- Unity 6 workflow: **File > Build Profiles > Add Build Profile (iOS) > Switch Profile**, then **Build** (Xcode project only) or **Build and Run** (device install). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html]
- Before building, set the **Bundle Identifier** in iOS Player Settings and pick device vs simulator via the **SDK version** field. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html]
- Re-export modes: **Replace** wipes the output folder; **Append** regenerates root files, `Data`, and `Libraries` while preserving the `classes` subdirectory; Append only works across projects generated by the same Unity iOS version. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html]
- **Generated Xcode targets**: `Unity-iPhone` (thin launcher app containing MainApp, launch screens, icons, Info.plist), `UnityFramework` (builds `UnityFramework.framework`; contains the Unity runtime, `Classes`, `Libraries`), and `GameAssembly` (C#-translated-to-C++ code; builds `libGameAssembly.a` and `il2cpp.a`). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/StructureOfXcodeProject.html]
- Key folders: `Classes` (entry points `main.mm`, `UnityAppController.mm/h`), `Data` (serialized assets + `.dat` assemblies — regenerated each build, don't modify), `Libraries` (regenerated), `Frameworks` (`UnityRuntime.framework`). The app `Info.plist` is **updated, not replaced**, on re-build. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/StructureOfXcodeProject.html]
- Command-line drive of the generated project: `xcodebuild test -destination "platform=iOS,id=<device-id>" -scheme Unity-iPhone`. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html]
- Xcode build-setting overrides use target-suffixed names — e.g. `PRODUCT_NAME_APP`, `PROVISIONING_PROFILE_APP`, `PROVISIONING_PROFILE_SPECIFIER_APP`, `OTHER_LDFLAGS_FRAMEWORK` (suffix `_APP` for the app target, `_FRAMEWORK` for UnityFramework). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/iphone-BuildProcess.html]
- [inferred] App Store submission itself follows the standard Xcode flow (Archive → Organizer → upload to App Store Connect, plus App Store Connect metadata/App Privacy questionnaire); the fetched Unity pages stop at "distribute it on the App Store", so treat the exact upload path as [inferred] and verify against App Store Connect docs at build time.

### 1.4 Signing: automatic vs manual provisioning

- Unity UI fields (Player Settings > iOS > Configuration/Identification in 6.6): **Signing Team ID** ("Enter your Apple Developer Team ID") and **Automatically Sign** ("Enable this option to instruct Xcode to automatically sign your build"). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsiOS.html]
- Backing Scripting API (exact members): `PlayerSettings.iOS.appleDeveloperTeamID`, `PlayerSettings.iOS.appleEnableAutomaticSigning`, `PlayerSettings.iOS.iOSManualProvisioningProfileID`, `PlayerSettings.iOS.iOSManualProvisioningProfileType` (plus `tvOSManualProvisioningProfileID/Type` and `VisionOSManualProvisioningProfileID/Type`; there is **no** `appleSigningTeamID` member). [confirmed: https://docs.unity3d.com/6000.6/Documentation/ScriptReference/PlayerSettings.iOS.html]
- [inferred] Automatic signing (Team ID + Automatically Sign) delegates certificate/profile management to Xcode ("Automatically manage signing"); manual mode means exporting your own provisioning profiles from the Apple Developer portal and wiring `iOSManualProvisioningProfileID` / `PROVISIONING_PROFILE_SPECIFIER_APP` into the generated project.
- Capabilities: "Automatically add capabilities" generates an `entitlements.plist` and adds Game Center capabilities when detected in the project. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsiOS.html]

### 1.5 Privacy manifests and required reason APIs

- Apple policy: "Since May 1, 2024 — You'll need to include approved reasons for the listed APIs used by your app's code (including from third-party SDKs) to upload a new or updated app to App Store Connect." [confirmed: https://developer.apple.com/news/upcoming-requirements/]
- Required-reason APIs are declared under `NSPrivacyAccessedAPITypes` in a `PrivacyInfo.xcprivacy` bundle file, with per-category keys `NSPrivacyAccessedAPIType` + `NSPrivacyAccessedAPITypeReasons`; the categories include FileTimestamp, SystemBootTime, DiskSpace, ActiveKeyboards, and UserDefaults. [confirmed: https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api — quote from official excerpt: "Starting May 1, 2024 … For each category of required reason API that your app or third-party SDK uses, add a dictionary to the NSPrivacyAccessedAPITypes"] (Apple's developer docs are JS-rendered; treat code-level lists as [confirmed] only for keys quoted above.)
- **Unity's engine manifest declares these reason codes automatically**: File timestamp `0A2A.1` ("Used by C# timestamp APIs") and `C617.1` ("Used to check files"); User defaults `CA92.1` ("Used for PlayerPrefs API"); System boot time `35F9.1`; Disk space `E174.1` ("Used to check disk space for AssetBundles"). Auto-included from Editor versions **2021.3.35f1, 2022.3.18f1, 2023.2.7f1** onward (so any 6.x build includes them). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/apple-privacy-manifest-policy.html]
- Developer obligations Unity cannot cover: declare required-reason usage of your **own native code**, and of **C# .NET APIs that map to the File timestamp category** (`fileInfo.CreationTime`, `.LastAccessTime`, `.LastWriteTime`, their `Utc` variants, and `File.Get*`/`Directory.Get*` timestamp calls). Your own manifest goes in the **Assets/Plugins** folder (iOS platform); third-party SDKs must ship their own manifests, and it is your responsibility to verify them. Undeclared usage → "your application might be rejected by the App Store." [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/apple-privacy-manifest-policy.html]
- [inferred] For a physics toy game like Balance Stack Hero clone: expect the Unity defaults to cover engine usage; audit any ad/analytics SDK plug-ins for their own `PrivacyInfo.xcprivacy`, and audit gameplay code for `File.Get*` timestamp calls.

### 2.4 AAB vs APK and Google Play requirements

- **"Google Play requires new applications to be an Android App Bundle (AAB) instead of an APK."** [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/android-distribution-google-play.html] Google's own statement: "From August 2021, new apps are required to publish with the Android App Bundle on Google Play." [confirmed: https://developer.android.com/guide/app-bundle]
- Unity AAB checklist: enable **Build App Bundle (Google Play)** in Build Profiles; "Make sure **Development Build** setting is disabled as otherwise the application upload might fail." [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/android-distribution-google-play.html]
- Size limits: APK path — "the APK must be smaller than 100 MB" (expansion file < 2 GB); AAB path — "the base module inside the AAB must be smaller than 200 MB"; Google's AAB compressed-download budget is 4 GB (base + configuration APKs). [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/android-distribution-google-play.html and https://developer.android.com/guide/app-bundle]
- Target API floor (current as of writing, Sept 2026): **"New apps and app updates must target Android 16 (API level 36) or higher"** on Google Play from **August 31, 2026**; existing apps must target API 35+ to stay available to new users; an extension form can push to **November 1, 2026**; internal-only private apps are exempt. [confirmed: https://developer.android.com/google/play/requirements/target-sdk] → [inferred] set Unity's **Target API Level** to 36 (Unity 6.6 supports targeting 35/36, and ships SDK platform "API 36" via Hub).
- 16 KB page-size enforcement (Google): all apps targeting Android 15 (API 35)+ must support 16 KB page sizes on 64-bit devices; **"Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates."** NDK r28+ aligns by default; r27 and lower need `-Wl,-z,max-page-size=16384` linker flags — relevant because Unity 6.6 ships NDK r27c. [confirmed: https://developer.android.com/guide/practices/page-sizes] [inferred] Unity's own 16 KB support statement (2.1) plus recent patch guidance covers the engine binaries; audit third-party `.so` plug-ins yourself.
- Extra Unity Play integrations: **Symbols size threshold** warning setting; **texture-compression targeting** for AAB auto-creates install-time asset pack `UnityTextureCompressionsAssetPack`; **"Report Dependencies in App Bundle"** Publishing-Settings toggle. [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/android-distribution-google-play.html]

Required: `-projectPath <pathname>` and `-quit`; recommended: `-batchmode`, `-logFile <path>` [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/build-command-line.html].

Canonical examples from the page (paths are placeholders for your installed version):

```bat
"C:\Program Files\Unity\Hub\Editor\6000.3.XXf1\Editor\Unity.exe" -executeMethod BuildScripts.BuildWindows64 -buildTarget StandaloneWindows64 -batchmode -quit -projectPath "C:\path\to\Project" -logFile C:\Logs\build.log
```
```bash
/Applications/Unity/Hub/Editor/6000.3.XXf1/Unity.app/Contents/MacOS/Unity -executeMethod BuildScripts.BuildMacOS -buildTarget StandaloneOSX -batchmode -quit -projectPath "/path/to/Project" -logFile ~/Logs/build.log
```

**Critical batch-mode limitation (new guidance):** always specify the build profile or target on the command line; you **cannot build multiple targets in one invocation**, and target-switching mid-script does not work because a recompile/reload cannot occur while a script runs. The page explicitly lists these APIs as unreliable in that context: `BuildProfile.SetActiveBuildProfile`, `EditorUserBuildSettings.SwitchActiveBuildTargetAsync`, `BuildAssetBundlesParameters.targetPlatform`, and `BuildPlayerOptions.target`; also warns that conditional-compilation symbols and loaded assemblies follow the **active** target, causing hard-to-diagnose output differences [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/build-command-line.html].

## 4. Build pipeline scripting API

`BuildPipeline.BuildPlayer` (Unity 6.6, [confirmed: https://docs.unity3d.com/6000.6/Documentation/ScriptReference/BuildPipeline.BuildPlayer.html]):
- Overloads: `BuildReport BuildPlayer(BuildPlayerWithProfileOptions)` (profile-driven, the Unity 6-native style), `BuildReport BuildPlayer(BuildPlayerOptions)`, and a legacy `BuildReport BuildPlayer(EditorBuildSettingsScene[] levels, string locationPathName, BuildTarget target, BuildOptions options)` which "is still supported, but will be replaced."
- Returns a `BuildReport`; `report.summary` (`BuildSummary`) exposes `result` (`BuildResult.Succeeded`/`BuildResult.Failed`) and `totalSize`.
- Calling it invalidates serialized-object references (e.g. cached `GameObject` variables); scripting-symbol changes need a domain reload before taking effect; built-in symbols of the **active** target persist even when building for a different target.
- Supported callbacks include `BuildPlayerProcessor`, `IPreprocessBuildWithContext`, `IProcessSceneWithReport`, `IPostprocessBuildWithContext` (names as printed on the 6.6 page).

`BuildPlayerOptions` struct fields (Unity 6.6, [confirmed: https://docs.unity3d.com/6000.6/Documentation/ScriptReference/BuildPlayerOptions.html]): `target`, `targetGroup`, `subtarget`, `scenes`, `locationPathName`, `assetBundleManifestPath`, `options`, `extraScriptingDefines`, `previousBuildReportDirectories`. **Correction for the plan:** there is **no** `outputFile`/`buildPath` field on `BuildPlayerOptions` (those names appeared in the research prompt; docs list `locationPathName` instead).

### Copy-paste C# BuildScript skeleton

```csharp
#if UNITY_EDITOR
using System;
using System.Linq;
using UnityEditor;
using UnityEditor.Build.Reporting;
using UnityEngine;

namespace BalanceStackHero.EditorTools
{
    /// Invoke via:  Unity.exe -batchmode -nographics -projectPath . -buildTarget <t>
    ///               -executeMethod BalanceStackHero.EditorTools.BuildScript.BuildWindows -quit -logFile build.log
    /// Throwing exits Unity with code 1 (confirmed: EditorCommandLineArguments -executeMethod docs).
    public static class BuildScript
    {
        const string OutputRoot = "Builds";

        // EditorBuildSettings.scenes / activeBuildTarget are standard APIs [inferred];
        // field/method shapes below are all [confirmed] per 6.6 API pages cited in §3–4.
        static string[] EnabledScenes() =>
            EditorBuildSettings.scenes.Where(s => s.enabled).Select(s => s.path).ToArray();

        public static void BuildWindows() => Build(BuildTarget.StandaloneWindows64, "Windows/BalanceStackHero2026.exe");
        public static void BuildMac()     => Build(BuildTarget.StandaloneOSX,      "MacOS/BalanceStackHero2026.app");
        public static void BuildLinux()   => Build(BuildTarget.StandaloneLinux64,  "Linux/BalanceStackHero2026.x86_64");
        public static void BuildAndroid() => Build(BuildTarget.Android,            "Android/BalanceStackHero2026.apk");
        public static void BuildWebGL()   => Build(BuildTarget.WebGL,              "WebGL");
        public static void BuildiOS()     => Build(BuildTarget.iOS,                "iOS"); // generates an Xcode project; run on macOS (IL2CPP same-OS rule, §5)

        static void Build(BuildTarget target, string relativePath)
        {
            if (EditorUserBuildSettings.activeBuildTarget != target)
                throw new InvalidOperationException(
                    $"Active target is '{EditorUserBuildSettings.activeBuildTarget}', expected '{target}'. " +
                    "Pass -buildTarget on the command line instead of switching mid-run " +
                    "(recompile/reload cannot happen inside -executeMethod).");

            var options = new BuildPlayerOptions
            {
                scenes = EnabledScenes(),
                locationPathName = $"{OutputRoot}/{relativePath}",
                target = target,
                options = BuildOptions.None,
            };

            BuildReport report = BuildPipeline.BuildPlayer(options);
            BuildSummary summary = report.summary;
            Debug.Log($"[BuildScript] {summary.result} — {summary.totalSize / (1024 * 1024)} MB");
            if (summary.result != BuildResult.Succeeded)
                throw new Exception($"Build failed: {summary.result}");
        }
    }
}
#endif
```

## 5. IL2CPP code generation

- IL2CPP is Unity's custom ahead-of-time (AOT) scripting backend, built for targets that can't JIT (e.g. iOS). Pipeline: Roslyn → managed DLLs → managed code stripping → IL2CPP translates all managed code to C++ → platform compiler builds it with the IL2CPP runtime into an executable or DLL. "Supported on all platforms"; cross-compilation generally unsupported (build on the same OS you target; Linux desktop is the documented exception via its cross-compiler) [confirmed: https://docs.unity3d.com/6000.5/Documentation/Manual/il2cpp-introduction.html].
- **IL2CPP Code Generation setting**: default "Optimize for runtime speed"; alternative "Optimize for code size and build time" emits less machine code at some runtime cost, "significantly reducing build times and binary size." Linux-only lever: IL2CPP LTO Mode `Thin` vs `Full`. Build-time tips: exclude project/build folders from anti-malware scans, use fast storage [confirmed: same URL].
- Scripting API: enum `Build.Il2CppCodeGeneration` with `OptimizeSpeed`/`OptimizeSize`, set per named build target group via `PlayerSettings.SetIl2CppCodeGeneration` [confirmed: https://docs.unity3d.com/6000.6/Documentation/ScriptReference/PlayerSettings.SetIl2CppCodeGeneration.html; enum confirmed via search index https://docs.unity3d.com/2023.2/Documentation/ScriptReference/Build.Il2CppCodeGeneration.html].
- Doc-slug drift to remember when citing: `Manual/IL2CPP.html` (2023.x) → `scripting-backends-il2cpp.html` (6000.1) → `il2cpp-introduction.html` (6000.5+); "Additional IL2CPP compiler arguments" exists at `handling-IL2CPP-additional-args.html` (6000.7) [confirmed: search-indexed pages above].
- `[inferred]` For our clone: WebGL builds also use IL2CPP, and the "Optimize for code size and build time" mode directly cuts CI wall-clock time — worth defaulting it on for prototype CI and flipping to speed for release candidates.

## 6. Licensing for CI (the pain point)

- **CLI activation flags remain official** in Unity 6.x for **Pro/named-user**: `-quit -batchmode -serial <KEY> -username 'email' -password 'pw'`; bare `-serial` (no key) activates a named-user license without its serial; `-quit -batchmode -returnlicense -username ... -password ...` returns it. Steps: ensure the license-file folder exists and is writable, run, wait for the license server, check `Editor.log` on failure [confirmed: https://docs.unity.com/en-us/engine/6000.7/manual/get-started/install-and-upgrade/licenses-and-activation/managing-your-unity-license; same flags listed on https://docs.unity3d.com/6000.6/Documentation/Manual/EditorCommandLineArguments.html].
- **Manual (offline) three-step flow**: create a license request file, generate the license file against your Unity ID, then activate with `-manualLicenseFile <file.ulf|.xml>`; the 6.6 Editor page describes step one as `-createManualActivationFile`, while the 6000.2 page shows a step-one flag named `-manualLicenseRequestFile` — **flag naming varies across 6.x docs; verify against the exact Editor build's page before scripting** [confirmed: https://docs.unity3d.com/6000.6/Documentation/Manual/EditorCommandLineArguments.html; request-file spelling: https://docs.unity3d.com/6000.2/Documentation/Manual/EditorCommandLineArguments.html].
- **Unity Personal**: the command-line activation/return procedures explicitly "do not apply to Unity Personal" — Hub login is the supported path; forum guidance confirms the `.alf`/`.ulf` route no longer covers Personal [confirmed: https://docs.unity.com/en-us/engine/6000.7/manual/get-started/install-and-upgrade/licenses-and-activation/managing-your-unity-license; community: https://discussions.unity.com/t/unity-no-longer-supports-manual-activation-of-personal-licenses/926760].
- **License file locations** (for reuse/paste into CI secrets): Windows `%PROGRAMDATA%\Unity\Unity_lic.ulf`; Linux `~/.local/share/unity3d/Unity/Unity_lic.ulf`; macOS `/Library/Application Support/Unity/Unity_lic.ulf` [confirmed: https://game.ci/docs/github/activation/ (community-run, paths cross-checked against Unity's ActivationFAQ page https://docs.unity3d.com/6000.6/Documentation/Manual/ActivationFAQ.html)].
- **Unity Licensing Client**: the Editor (2021.2+/6.x) talks to a Licensing Client component; configuration flags (`-config-path` etc.) live in the Licensing Server docs, and the new Unity CLI "detects and replaces a stale Unity Licensing Client automatically" [confirmed: https://docs.unity.com/en-us/licensing-server/client-config; community/forum rollout note: https://discussions.unity.com/t/unity-cli-1-0-0-beta-6-is-rolling-out/1734486].
- `[inferred]` Planning call for this project: assume a Plus/Pro seat so CI can use the documented `-username/-password/-serial` or `.ulf`-file paths; do **not** design GitHub Actions around a Personal license.

## 7. The new Unity CLI (experimental) — [confirmed: https://docs.unity.com/en-us/unity-cli/unity-cli-reference]

- Standalone `unity` binary, no Hub app required; **marked experimental** on the reference page. Replaces `Unity Hub.exe -- --headless` (breaking migration: `install -v <v>` → `unity install <v>` positional; `install-modules -v` → `-e <editor>`; removed `--headless`, `--silent`, etc.).
- Key commands: `unity install lts` / `unity install 6000.3.7f1 -m ios android webgl --cm` (modules, incl. child modules like Android SDK/NDK); `unity install-modules -e <v> -m <ids>`; `unity editors -i`; `unity projects create MyGame [--no-cloud]` (default creates a Unity Cloud project — fails with **exit code 3** when not signed in); `unity open ./MyProject` (`--wait` on macOS/Linux: 0 clean, 6 fail; **Windows `--wait` not supported — exits 2**); plus `build`, `run`, `recompile`, `test` (supports `--affected` via `watch test`), `auth login|status|logout`, `license`, `pipeline`, `command(s)`, `doctor`, `logs`, `config`, `mcp`, `self-update` [confirmed: same URL; create/open/auth examples: https://docs.unity.com/en-us/unity-cli/use-unity-cli].
- CI-friendly output: global `--format json|ndjson|tsv|github|human` (`--github` gives Actions annotations; piped stdout defaults to **tsv**). JSON envelope: `success, command, data, errors, warnings` [confirmed: reference page].
- Exit codes: `0` success; `1` general; `2` usage error; `3` auth; `4` config required; `6` primary operation failed; `7` service unreachable (safe to retry); `8` `unity test` ran with failures (never retry); `130`/`143` signals [confirmed: same URL].
- Unattended auth: env vars `UNITY_SERVICE_ACCOUNT_ID` + `UNITY_SERVICE_ACCOUNT_SECRET`; also `UNITY_NON_INTERACTIVE`, `UNITY_PROJECT_PATH`, `UNITY_QUIET`; flags beat env vars [confirmed: same URL].
- Editor control needs the **`com.unity.pipeline` package** (Unity 6.0+, server on port **7800**, installed via `unity pipeline install`; remote Editor commands include `eval`/`eval_file`; target one of several Editors with `unity command --project-path=<path>`) [confirmed: https://docs.unity.com/en-us/unity-production-pipeline/local-tools-cli/unity-pipeline-package].

## 9. GameCI (community, de-facto standard) — [community]

- `game-ci/unity-builder@v4` (repo self-describes as "a GitHub Action to build Unity projects for different platforms", ~1.1k stars [confirmed: https://github.com/game-ci/unity-builder]).
- Inputs (per docs page): required `targetPlatform`; `unityVersion` (default `auto`), `projectPath`, `buildProfile`, `buildName` (default `<build_target>`), `buildsPath` (default `build`), `buildMethod` (custom `-executeMethod`), `customParameters`, `versioning` (`Semantic|Tag|Custom|None`), Android suite (`androidVersionCode`, `androidExportType`, `androidKeystoreName`, `androidKeystoreBase64`, `androidKeystorePass`, `androidKeyaliasName`, `androidKeyaliasPass`, `androidTargetSdkVersion`, `androidSymbolType`), licensing/server (`unityLicensingServer`, `skipActivation`), container knobs (`containerRegistryRepository` default `unityci/editor`, `containerRegistryImageVersion` default `3`, `dockerWorkspacePath` default `/github/workspace`, `dockerCpuLimit`, `dockerMemoryLimit`, `dockerIsolationMode`, `useHostNetwork`, `runAsHostUser`, `chownFilesTo`), and `allowDirtyBuild` [confirmed: https://game.ci/docs/github/builder].

GameCI states it "does not acquire nor store your Unity email, password, or license file contents"; builder/test-runner actions embed activation + license return; licenses aren't OS/version-bound [confirmed: https://game.ci/docs/github/activation/].
- Runs Unity in Linux/Windows **editor containers** with a macOS host path; caching the project `Library/` folder via `actions/cache@v3` reportedly "speeds up builds by more than 50%" [confirmed: https://game.ci/docs/github/builder].

## 10. Copy-paste GitHub Actions example (GameCI v4, WebGL + editmode tests)

Inputs, secrets, and cache paths below are exactly those confirmed on game.ci pages; `actions/checkout@v4` / `actions/upload-artifact@v4` are standard Actions, `[inferred]` versions.

```yaml
name: CI
on: [push, pull_request]
jobs:
  test:
    name: EditMode tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Cache Library
        uses: actions/cache@v3
        with:
          path: path/to/your/project/Library
          key: Library-BalanceStackHero-Test
          restore-keys: |
            Library-BalanceStackHero-
            Library-
      - name: Run tests
        uses: game-ci/unity-test-runner@v4
        env:
          UNITY_LICENSE: ${{ secrets.UNITY_LICENSE }}
          UNITY_EMAIL: ${{ secrets.UNITY_EMAIL }}
          UNITY_PASSWORD: ${{ secrets.UNITY_PASSWORD }}
        with:
          projectPath: path/to/your/project
          githubToken: ${{ secrets.GITHUB_TOKEN }}

  build:
    name: Build ${{ matrix.targetPlatform }}
    needs: test
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        targetPlatform: [WebGL, StandaloneWindows64, StandaloneOSX, Android, iOS]  # docs list all seven standalone/mobile targets
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true
      - uses: actions/cache@v3
        with:
          path: path/to/your/project/Library
          key: Library-BalanceStackHero-${{ matrix.targetPlatform }}
          restore-keys: |
            Library-BalanceStackHero-
            Library-
      - uses: game-ci/unity-builder@v4
        env:
          UNITY_LICENSE: ${{ secrets.UNITY_LICENSE }}
          UNITY_EMAIL: ${{ secrets.UNITY_EMAIL }}
          UNITY_PASSWORD: ${{ secrets.UNITY_PASSWORD }}
        with:
          targetPlatform: ${{ matrix.targetPlatform }}
          buildName: BalanceStackHero2026
          buildsPath: build
      - uses: actions/upload-artifact@v4
        with:
          name: build-${{ matrix.targetPlatform }}
          path: build/${{ matrix.targetPlatform }}
```

Note: `game-ci/unity-test-runner@v4` exists in the same ecosystem (referenced by GameCI docs and its GitHub issues) `[community: https://github.com/game-ci/unity-test-runner/issues/162]`; verify its inputs at setup time. `[inferred]`

## 11. Test automation flags (Test Framework 1.4.6)

[confirmed: https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html] — `-runTests` ("Runs tests in the Project"); `-testPlatform` accepts `EditMode`, `PlayMode`, or any `BuildTarget` enum value (defaults to EditMode if omitted); `-testResults <path>` writes NUnit-format XML (default: project root); `-testFilter` / `-testCategory` take semicolon-separated names or regexes with `!` negation (both must match when combined); `-assemblyNames`; `-playerHeartbeatTimeout` (default 10 min); `-runSynchronously` (EditMode only); `-testSettingsFile` (`TestSettings.json`); `-orderedTestListFile`; `-randomOrderSeed`; `-retry`/`-repeat`. `-testBuildTimeout`/`-testRunnerPlatform` do **not** appear in this reference. Canonical example (quoted): `Unity.exe -runTests -batchmode -projectPath PATH_TO_YOUR_PROJECT -testResults C:\temp\results.xml -testPlatform PS4`.
Exit codes: the docs state "there is no exit-code standard" `[confirmed: same URL]`; in practice Unity returns **0** pass / **2** failed-or-inconclusive / **3** run error, with the inconclusive→2 behavior confirmed in the package changelog [confirmed: https://docs.unity3d.com/Packages/com.unity.test-framework@1.1/changelog/CHANGELOG.html] and the 0/2/3 mapping from Unity staff [community: https://discussions.unity.com/t/batch-mode-tests-fail/794313]. ## 0. Critical premise correction (read first)

The orchestrating task assumes an "official Unity MCP server" at **`github.com/Unity-Technologies/mcp-for-unity`** that exposes snake_case tools like `manage_scene` / `manage_gameobject`. That combined premise is **false in every part**, and conflates three different things:

1. **No such repository exists.** `https://github.com/Unity-Technologies/mcp-for-unity` returns HTTP 404 [confirmed: https://github.com/Unity-Technologies/mcp-for-unity], and a GitHub search of the Unity-Technologies org for repos matching "mcp" returns `total_count: 0` [confirmed: GitHub REST API `search/repositories?q=mcp+org:Unity-Technologies`, queried 2026-09-24].
2. **Unity's actual official MCP server** shipped inside the in-editor **AI Assistant package `com.unity.ai.assistant`** — and it is **now deprecated**, replaced by the **Unity CLI's `unity mcp` mode** (Section 4).
3. **The tool names in the task list** (`manage_editor`, `manage_scene`, `manage_gameobject`, `manage_asset`, `manage_prefabs`, `manage_material`, `manage_shader`, `execute_menu_item`, `read_console`, `run_tests`) are the exposed tools of **`CoplayDev/unity-mcp` ("MCP for Unity")** — a **third-party, MIT-licensed project explicitly "not affiliated with Unity Technologies"** [confirmed: https://coplaydev.github.io/unity-mcp/ ; https://openupm.com/packages/com.coplaydev.unity-mcp/]. It is the dominant community Unity MCP bridge (14,459 stars as of 2026-09-24 [confirmed: GitHub API]).

Where did "mcp-for-unity" come from? It is the **Python console-script name** of Coplay's server package: the official stdio config runs `uvx --from mcpforunityserver mcp-for-unity --transport stdio` [confirmed: https://coplaydev.github.io/unity-mcp/getting-started/install]. `[inferred]` The task likely back-formed a fake org repo (`Unity-Technologies/mcp-for-unity`) from that script name.

Three genuinely "official" Unity artifacts exist and should not be confused:

| Artifact | What it is | Status (Sep 2026) |
|---|---|---|
| `com.unity.ai.assistant` in-editor MCP server | MCP server hosted inside the Editor | **Deprecated** [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html] |
| **Unity CLI `unity mcp`** + `com.unity.pipeline` | CLI-hosted MCP server driving the Editor over local HTTP | **Current official path forward** [confirmed: https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli] |
| `Unity-Technologies/unity-agent-plugin` | Official **Claude Code / Codex plugin of Unity skills** — *not* an MCP server (345 stars, updated 2026-09-24) | Active beta (0.1.6-beta) [confirmed: https://github.com/Unity-Technologies/unity-agent-plugin] |

## 1. The official in-editor Unity MCP server (`com.unity.ai.assistant`)

**What it is:** "Unity MCP connects large language model (LLM)-based agents, such as Claude Code and Cursor, to the Unity Editor through standardized MCP tools" — the server Unity *exposes* (distinct from the "MCP Servers" page under *AI > MCP Client*, which configures servers the Assistant *consumes*) [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.0/manual/unity-mcp-overview.html].

**Package & docs location:** the server lives in `com.unity.ai.assistant`; manual pages are published both as package docs on docs.unity3d.com (versions 2.0.0-pre.1 → 2.20, latest at fetch time) and summarized on docs.unity.com/en-us [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html].

**Preconditions (all from official sources):**
- **Unity 6 (6000.0) or later** with the AI Assistant package installed [confirmed: https://unity.com/blog/unity-ai-mcp-how-to-get-started].
- **The Editor must be running** — the "Unity Bridge" "starts automatically when the Editor loads"; Project Settings shows it as *Running* (green) or *Stopped* [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html].
- **Project connected to Unity Cloud** [confirmed: https://unity.com/blog/unity-ai-mcp-how-to-get-started].
- **A paid/eligible subscription with an assigned seat:** "AI Gateway and MCP access require an eligible Unity subscription and an assigned seat… AI Gateway and MCP features require an explicitly assigned seat" (relevant AI, Unity Pro, Enterprise, or Industry subscriptions); the beta additionally required an active trial/subscription to Unity's AI tools [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.9/manual/integration/ai-gateway-get-started.html ; https://unity.com/blog/unity-ai-mcp-how-to-get-started].
- **The task's "Create for Game Development enabled" precondition is `[not found / unverified]`:** no Unity SKU by that literal name appears in official docs or on unity.com/products (game-dev plans remain **Personal / Pro / Enterprise**, with Industry for non-game) [confirmed: https://unity.com/products]. Treat the phrase as a planning-doc error.

**Runtime architecture (verified — and it is NOT a WebSocket):**
- Flow: **AI client → MCP over stdio → relay binary (`~/.unity/relay/`, run with `--mcp`) → local IPC channel → in-editor Unity Bridge → McpToolRegistry → tools** [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.0/manual/unity-mcp-overview.html].
- The Editor bridge "opens a local interprocess communication (IPC) channel"; the transport is **named pipes on Windows, Unix sockets on macOS/Linux** — no WebSocket and no TCP port is used [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-overview.html].
- The relay binary is installed by Unity to `~/.unity/relay/` on Editor start; `--mcp` selects its MCP-server mode [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html].
- Security: direct client connections require a one-time **Allow** on a "Pending Connection" in Project Settings (remembered later); connections through Unity's AI Gateway are auto-approved; multiple MCP clients may connect to one Editor instance; per-tool enable/disable toggles live under **Edit > Project Settings > AI > Unity MCP Server** [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.0/manual/unity-mcp-overview.html ; …/2.19/manual/integration/unity-mcp-get-started.html].

**Required MCP configuration JSON (exactly as documented):**
```json
{
  "mcpServers": {
    "unity-mcp": {
      "command": "<HOME_ABSOLUTE_PATH>/.unity/relay/relay_mac_arm64.app/Contents/MacOS/relay_mac_arm64",
      "args": ["--mcp"]
    }
  }
}
```
[confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html]. Variants shown on the same page: target a project via `"args": ["--mcp", "--project-path", "/Users/me/MyUnityProject"]` or via `"env": { "UNITY_PROJECT_PATH": "/Users/me/MyUnityProject" }`; instance selection by PID uses `--instance-id <pid>` / `UNITY_INSTANCE_ID` (CLI arg wins over env). Absolute paths are required because "~" may not be expanded by every client. Per-platform relay executables: `relay_mac_arm64` / `relay_mac_x64` (.app bundles), Windows `%USERPROFILE%\.unity\relay\relay_win.exe`, Linux `~/.unity/relay/relay_linux` [confirmed: same page; also https://unity.com/blog/unity-ai-mcp-how-to-get-started]. For **Claude Code and Cursor**, the Editor's *Integrations* section offers one-click **Configure** (also listed: Windsurf, Claude Desktop; screenshots show VS Code Copilot, Kiro, Codex, Gemini); the manual JSON above goes into the client's own config file — e.g. `.cursor/mcp.json` / `.mcp.json` `[inferred — file locations not named on this page]`. On our Windows dev box the command would be `C:\Users\<you>\.unity\relay\relay_win.exe` with args `["--mcp"]` [confirmed path pattern, inferred assembly].

**Exposed tools:** official docs do **not** publish a full per-tool list on the fetched pages; they describe categories — "scene management, asset operations, script editing, and console access" plus build-settings inspection and C# custom-tool registration [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.0/manual/unity-mcp-overview.html]. Named example tools appear as **`Unity_ManageScene`, `Unity_ManageGameObject`, `Unity_ReadConsole`** (the `Unity_`/`Unity.` prefix + PascalCase naming style, unlike Coplay's snake_case) [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html ; https://unity.com/blog/unity-ai-mcp-how-to-get-started]. Custom tools are registered in C# via attributes/interfaces/runtime APIs and appear dynamically [confirmed: overview page, same URL].

## 2. Deprecation: `unity mcp` (Unity CLI) is the official successor

The current manual states plainly: "**Unity MCP server is deprecated**" — "Use the Unity command-line interface (CLI) instead," citing "faster iteration times, improved stability, and the ability to target runtime and the Editor" [confirmed: https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-get-started.html ; …/mcp-configure.html]. Scope of the deprecation [confirmed: https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli]:
- **Affected:** the in-editor MCP server component of `com.unity.ai.assistant`.
- **Not affected:** third-party MCP packages from GitHub (i.e., Coplay stays usable), and `unity mcp` / `unity command` from the Unity CLI (not deprecated).
- `unity command` and `unity eval` drive the Editor **without MCP** and are "faster and use fewer tokens than MCP" — recommended where the agent can run shell commands.

**Migration commands (exact):**
```bash
unity pipeline install        # install/configure the com.unity.pipeline package
unity mcp configure <client>  # <client> = claude | cursor | vscode | windsurf
unity mcp configure --list    # supported clients + config status
unity skill install <agent-name>
```
[confirmed: https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli]. This "updates the client's configuration file to use the Unity CLI's MCP server instead of the in-Editor MCP server." Requirements/pricing: driving a running Editor needs **Unity 6.0 LTS or later**; the CLI/Pipeline MCP is **free, separate from Unity AI subscriptions**, localhost-only, and AI Assistant package **2.13+** is required to avoid a CLI/in-editor package conflict [confirmed: same URL].

**How it works:** the Pipeline package "turns your running Editor into a local HTTP server" that survives domain reloads; default status line `Unity Editor (port 7800): ready` (verify with `unity status`) [confirmed: https://unity.com/resources/a-beginners-guide-to-unity-cli-and-the-pipeline-package]. Example verified combination: Unity CLI **1.0.0-beta.6** + `com.unity.pipeline` **0.5.0-exp.1** + Unity **6000.6.0b9**; CLI installs via `curl … public-cdn.cloud.unity3d.com/hub/prod/cli/install.sh` (macOS/Linux) or `irm …/install.ps1 | iex` (Windows), or Unity Hub [confirmed: same URL]. Forum staff add: "Both the CLI and MCP will be free, with no concurrency limits," MCP mode supports `--profile` tool subsets (e.g. `scene-management`, `build-pipeline`) so "the LLM only sees the 15–20 tools relevant to the task," and `unity command eval --code 'Debug.Log("…");'` runs C# on the main thread without a domain reload [confirmed: https://discussions.unity.com/t/announcing-the-unity-cli-a-new-way-to-connect-your-tools-and-agents/1731104 ; https://unity.com/resources/a-beginners-guide-to-unity-cli-and-the-pipeline-package — profile names from the staff thread are `[confirmed]` only as quoted in that thread, not on docs.unity.com].

**Planning implication [inferred]:** for *Balance Stack Hero 2026* on Unity 6.6, do **not** budget integration work around the in-editor AI-Assistant MCP server (deprecated + paywalled by seat assignment). Budget for **`unity mcp`/`unity command`** (free, localhost HTTP 7800) and/or the third-party Coplay bridge below.

## 3. CoplayDev/unity-mcp "MCP for Unity" — the project that actually has the task's tools

- **Identity:** MIT-licensed, "not affiliated with Unity Technologies"; repo `CoplayDev/unity-mcp`; UPM folder `MCPForUnity`; PyPI server package `mcpforunityserver`, console script `mcp-for-unity` [confirmed: https://github.com/CoplayDev/unity-mcp ; https://coplaydev.github.io/unity-mcp/getting-started/install].
- **Install (Editor side):** Package Manager git URL `https://github.com/CoplayDev/unity-mcp.git?path=/MCPForUnity#main` (pin `#v10.0.0`) or OpenUPM `openupm add com.coplaydev.unity-mcp` [confirmed: https://raw.githubusercontent.com/CoplayDev/unity-mcp/main/README.md].
- **Preconditions:** **Unity 2021.3 LTS → 6.x** (far broader than the official server's Unity 6-only floor), **Python 3.10+ with `uv`**, Git on PATH, an MCP client [confirmed: https://coplaydev.github.io/unity-mcp/getting-started/install]. No Unity subscription/seat requirement is documented (third-party, free) [confirmed: same].
- **Architecture — the real "WebSocket bridge":** MCP client ↔ Python server via **HTTP (default) at `http://localhost:8080/mcp`** or **stdio**; Python (FastMCP) hosts a **shared WebSocket hub at `/hub/plugin`** that the Unity Editor plugin connects to; multiple agents can share one Editor with per-`client_id` session state [confirmed: https://coplaydev.github.io/unity-mcp/architecture/transports ; https://coplaydev.github.io/unity-mcp/]. Stdio mode instead spawns a per-client Python process using a "legacy TCP bridge" (example instance shorthand `set_active_instance(instance="6401")` — 6401 is that bridge's example port), single-agent only [confirmed: transports page]. HTTP binds loopback by default; LAN/remote requires explicit opt-in toggles ("Allow LAN Bind", https-only) [confirmed: same].
- **Client config JSON (exact, from the install page):**
  - HTTP default (Cursor, Windsurf, VS Code, Cline, and **Claude Code** — the clients matrix lists Claude Code as HTTP + auto-config [confirmed: https://coplaydev.github.io/unity-mcp/getting-started/clients]):
    `{"mcpServers": {"unityMCP": {"url": "http://localhost:8080/mcp"}}}`
  - VS Code uses a `servers` key (not `mcpServers`) with `"type": "http"` + same URL [confirmed: same two pages].
  - stdio (Claude Desktop or no-HTTP clients), macOS/Linux:
    `{"mcpServers": {"unityMCP": {"command": "uvx", "args": ["--from", "mcpforunityserver", "mcp-for-unity", "--transport", "stdio"]}}}`; on Windows the documented command is the WinGet uvx path `C:/Users/YOUR_USERNAME/AppData/Local/Microsoft/WinGet/Links/uvx.exe` with the same args. **No `env` keys** appear in any documented snippet [confirmed: https://coplaydev.github.io/unity-mcp/getting-started/install].
  - Auto-config: in Editor, **Window → MCP for Unity → Configure All Detected Clients**; Cursor additionally needs the `unityMCP` server toggled on in *Cursor → Settings → MCP* after auto-config; Claude Code needs a restart if the transport is switched, and on macOS may need "Choose Claude Install Location" because Hub-launched Unity doesn't inherit the shell PATH [confirmed: https://coplaydev.github.io/unity-mcp/getting-started/clients ; https://coplaydev.github.io/unity-mcp/guides/claude-code-cli].
- **Tool catalog — 48 tools / 10 groups** (README says "47 focused entrypoints"; the reference page counts 48) [confirmed: https://coplaydev.github.io/unity-mcp/reference/tools]. Core (30): `apply_text_edits`, `batch_execute`, `create_script`, `debug_request_context`, `delete_script`, `execute_custom_tool`, `execute_menu_item`, `find_gameobjects`, `find_in_file`, `get_sha`, `manage_asset`, `manage_build`, `manage_camera`, `manage_components`, `manage_editor`, `manage_gameobject`, `manage_graphics`, `manage_material`, `manage_packages`, `manage_physics`, **`manage_prefabs`** (plural — the task's "manage_prefab" is wrong), `manage_scene`, `manage_script`, `manage_script_capabilities`, `manage_tools`, `read_console`, `refresh_unity`, `script_apply_edits`, `set_active_instance`, `validate_script`; plus `run_tests` + `get_test_job` (async test jobs), `manage_shader`/`manage_texture`/`manage_vfx` (vfx group), `manage_ui`, `manage_animation`, `manage_probuilder`, `manage_profiler`, `execute_code`/`manage_scriptable_object`, `unity_docs`/`unity_reflect`, and 5 AI asset-gen tools (`generate_image|model|audio`, `import_model[_file]`) [confirmed: same].
- **Task-name corrections against the catalog [confirmed]:** `manage_editor_theme` does **not** exist; `send_console_log` does **not** exist; `set_active_tool` exists only as an **action** of `manage_editor` (full action list: `telemetry_status`, `telemetry_ping`, `play`, `pause`, `stop`, `set_active_tool`, `add_tag`, `remove_tag`, `add_layer`, `remove_layer`, `deploy_package`, `restore_package`, `undo`, `redo`) [confirmed: https://coplaydev.github.io/unity-mcp/reference/tools/core/manage_editor]. Editor theme is instead a normal Unity preference an agent could set via `execute_code` `[inferred]`.

## 4. Version-difference and usage notes for the plan

- **Unity 6.x vs 6.6 tech stream:** official in-editor MCP floor is "Unity 6 (6000.0)+"; the CLI successor needs 6.0 LTS+ to drive a running Editor; live doc examples were produced on 6000.6.0b9 — i.e., the CLI is still **beta-versioned (1.0.0-beta.6 / pipeline 0.5.0-exp.1)** and fast-moving; pin versions and re-verify at build time [confirmed: URLs in §1–2; pinning advice `[inferred]`]. Unity 6.6 (our target) satisfies all stated floors [confirmed by "or later" wording; applicability to 6.6 specifically `[inferred]`].
- **`unity mcp configure claude`** is the sanctioned one-shot way to wire **Claude Code** (this session's harness) to Unity once the CLI ships at our target version; `--list` enumerates client support [confirmed: https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli].
- **Blender versions:** not applicable to this topic (no Blender MCP surface was researched here); covered in the DCC-pipeline doc. `[confirmed: n/a]`
- **Recommendation `[inferred]`:** for an indie budget and heavy agentic iteration, primary bet = **CoplayDev MCP for Unity** (free, no seat requirement, full documented tool catalog, WebSocket/HTTP bridge proven with Claude Code + Cursor); secondary = **Unity CLI `unity mcp`/`unity command`** for headless builds/tests and as the future-proof official surface; avoid depending on the deprecated `com.unity.ai.assistant` MCP server except for parity testing behind an AI seat.
