The decision engine: five questions before every call

An agent that picks tool calls one at a time, observes, and picks again is solving a sequential decision problem under partial observability. The formal object is a POMDP (glossary I) — and the classical result is that the optimal next-test policy is computationally out of reach, so practical systems use structured heuristics [S1]. BCF is one such heuristic: before each of the 24 calls, the same five questions run, in order, and the first one that changes the answer wins.

loopThe five questions, in priority order

  1. Which phase am I in? — spec / localize / patch / validate. The phase is the permission set: in spec, file tools are locked (G0); in patch, exploration reads require a plan. Tool permissions enforce the ladder; prompts merely describe it.
  2. What is the next unmet obligation? — an explicit checklist: hypotheses B1–B5 unconfirmed (localize) · next node in the fix_order DAG (patch) · next gate in G1–G6 (validate). One obligation per call, by design.
  3. Can I afford it? — budget_plan arithmetic: localization capped at 10 calls, force-submit at turn 42, rescue armed at 3 strikes / 25% budget. A call that busts the plan is not a candidate.
  4. Have I tried this and failed? — journal lookup: no tool call repeats a journaled failed action (tenet 3). This is the loop-breaker.
  5. Is there a cheaper tool answering the same question? — graph before grep (ids are pre-resolved); symbol queries before prose [V §8.2]; a 150-line read window before a whole-file read.

POMDPThe same loop, in the formal vocabulary [R]

hidden statethe graded truth: hidden test patch, full fault set, gold diff
observationstool outputs (search results, file lines, pytest exits)
belief statespec + journal + ledger — written down, not just felt
policythe five questions (this slide)
stopping rulegate vector all-true ⇔ submit (tenet 4)

Sequential-diagnosis research computes optimal test orderings by expected information gain and shows they beat fixed heuristics [S1]; troubleshooting-as-POMDP is a standing framework [S2, S3]. BCF's fixed ladder is the heuristic version — hypothesis H2 (slide 15) is the upgrade.

[V]The environment has its own loop rules

  • Context window 32,768 tokens; auto-compaction at 14,336; context cache TTL 1,800 s (HARNESS_README §7.2).
  • Text-only turns earn a nudge; >3 consecutive nudges = termination (§5.3). BCF's journal complements this: the harness stops stalls, the journal stops repeats.
◆ teachable moment — “policy” and “heuristic” are compliments, not insults A policy is any rule mapping what-you-know to what-you-do. A greedy reactive loop is a policy; the five questions are a policy; the computed-optimal VOI ordering is a policy. Heuristic just means “good-enough substitute for the optimum.” Calling BCF a heuristic policy places it in the literature rather than diminishing it — and it names exactly what H2 tries to improve.

◆ teachable moment — the spec is pre-registration, and that is not a metaphor Pre-registration (glossary I): commit your predictions to a fixed, timestamped artifact before seeing the data, so the data can prove you wrong. A registered clinical trial and the BCF spec do the same job: the spec pins down hypotheses, order, and validation before any file is opened, so later observations (like a scary local red) are scored against the spec instead of rewriting it after the fact. The self-sabotage revert of the naive run is exactly what pre-registration exists to prevent. The paper track should say this out loud — it is the project's cleanest conceptual bridge to experimental methodology.

◆ teachable moment — information gain, in one paragraph Entropy (glossary I) measures uncertainty about an answer — “which of these five hypotheses is true?” has more entropy before localization than after. A call has high information gain if the entropy you expect after seeing its result is much lower than now. A call that cannot change any belief — re-running the same grep — has zero gain no matter how productive it feels. The whole phase-2 ladder, and H2's upgrade, is just: spend calls where uncertainty actually drops.

◆ teachable moment — the ratchet, or why BCF almost never reverts A ratchet lets motion in one direction only. In code: nothing applied gets undone; failures route forward (fix, micro-check, rescue), never backward (revert). Why is that right here? Because reverting only pays when the hypothesis was wrong — and the spec already paid to test hypotheses. When the hypothesis is right and the signal is misleading (Trap 1), reverting is self-sabotage. The ratchet encodes that asymmetry as a rule instead of a mood.

DECISIONHow the order within validation was chosen

  • Rule: A5's verification hierarchy — cheapest decisive evidence first: contract repro (does the new API behave?) before any pytest; and migration before the first pytest run. That ordering is the trap-1 countermeasure: the red exists right now, one call away, in five old-API call sites — the plan steps over the rake instead of suppressing or discovering it.
  • Why migrate tests you know are discarded? Not sentiment: after migration, G4/G5 measure your actual change; before it, they would measure the rename's shadow. Five throwaway edits buy meaningful local evidence.
  • Gates are orchestrator code: G1 scope (files ∈ allowed), G2 git apply --check, G3 ast.parse per changed file — no model in the loop can grant approval. [R] This is the ACI guardrail pattern with measured double-digit value [S13].

GAINWhat the results buy

  • Knowledge: the new contract demonstrably works (repro), the migrated suite is green, adjacent modules unregressed — three independent evidence classes, none solely reliant on the suite that was about to lie.
  • State: gate vector G1–G6 all-true → submit unlocks. “Done” is a boolean computed from the vector, not a feeling (tenet 4).
  • Cleanliness: the repro lives in /tmp — the patch stays exactly the 8 intended files.
◆ teachable moment — tests are evidence, not truth The suite the agent can run is one instrument, with a known failure mode here (it targets the old API). Good experimental method doesn't discard a miscalibrated instrument — it recalibrates (migration), cross-checks (repro, adjacent suites), and keeps the specification as the reference standard. SpecBench builds an entire benchmark on this exact distinction between visible and held-out evidence [S10]; BCF's validation order is the same idea at run time.

Glossary I — decisions, evidence, experiments

POMDP S1–S3
A partially observable Markov decision process: a tuple (S, A, T, O, r, γ) — states S, actions A, transition function T(s'|s,a), observation function O(o|s',a), reward r, discount γ — where the agent never sees s directly, only o. In this project: the hidden state is the graded truth; tool outputs are o; BCF's five questions are the policy that maps beliefs to actions.
belief state S1
The probability distribution over hidden states given all observations so far; the sufficient statistic for acting optimally in a POMDP. Here: externalized as spec + journal + ledger — written down so it can be audited instead of merely felt.
policy
A rule π mapping belief states to actions (or action distributions). Reactive loops, checklists, and computed-optimal controllers are all policies. Here: slide 4's five questions = BCF's π; H2 proposes upgrading π's localization branch.
entropy
Shannon uncertainty of a distribution: H(X) = −Σ p(x) log p(x), in bits (log₂) — 0 when the answer is certain, maximal when all options are equally likely. Here: “which hypothesis is true?” before vs after a tool call.
information gain · value of information S1–S3
IG: expected entropy reduction from an observation: H(belief) − E[H(belief | result)]. VOI: the same idea priced — expected improvement in decision quality minus test cost. Here: the localization ladder is a hand-coded IG ordering; H2 makes the score explicit; zero-IG calls (repeats) are budget waste by definition.
sequential diagnosis / multi-hypothesis testing S1
The problem of choosing tests one at a time, updating beliefs after each, to identify a hidden cause at least cost; optimal policies are computable only for structured cases (low-dimensional belief manifolds) and beat fixed heuristics there. Here: the formal ancestor of “which tool call next.”
SBFL — spectrum-based fault localization S4–S8
Ranking program elements by suspiciousness scores computed from pass/fail spectra (e.g., Ochiai, Tarantula formulas over failed/passed test coverage). Established result: accuracy decays as fault count grows [S4]. Here: the baseline paradigm BCF's spec-first localization replaces when no failing tests exist to build a spectrum from.
reward hacking · specification gaming · test overfitting S10–S12
Reward hacking / spec gaming: scoring well by exploiting the evaluation process rather than doing the intended task. Test overfitting: its testing-instance — code that passes the observed tests while violating the specification [S11]. Here: why BCF treats the issue text, not the visible suite, as the contract — and why H3 synthesizes its own held-out-style tests.
self-consistency S23
Sample a diverse set of reasoning paths (temperature > 0), then take the answer most consistent across paths — marginalizing out the paths. Here: H1 applies it to the spec itself: three drafts, per-field votes.
pre-registration
Committing hypotheses, procedures, and analysis to a fixed, timestamped artifact before data collection, so outcomes can falsify rather than merely illustrate. Here: the BCF spec is pre-registration for the run; this package is pre-registration for the experiments (predictions marked [P]).

Glossary II — parameters, LoRA, fine-tuning, and friends

parameters (weights)
The learned numbers of a model — for a transformer, the entries of its weight matrices (plus biases). “31B” in gemma-4-31b-it-qat-w4a16-ct counts them. Training = adjusting parameters to lower a loss.
fine-tuning · full fine-tuning
Continuing training of a pretrained model on a narrower dataset. Full fine-tuning updates every parameter — powerful, but for a 31B model it means optimizer state for 31B numbers.
PEFT — parameter-efficient fine-tuning
The family of methods that update a small trainable addition while freezing the base weights — LoRA is the flagship member.
LoRA — Low-Rank Adaptation S16
Freeze the pretrained weight W₀ ∈ R^(d×k); learn only a low-rank update ΔW = B·A, with A ∈ R^(r×k), B ∈ R^(d×r), and rank r ≪ min(d,k); the layer computes W₀x + BAx. Reported: up to 10,000× fewer trainable parameters and 3× less GPU memory than full fine-tuning of GPT-3 175B, on-par-or-better quality, and no added inference latency (merge the update into W₀). In this project: the competition's sanctioned adaptation mechanism, served via vLLM multi-LoRA (§3.4) — with the standing canary-gate rule from the 2026-09-30 bug trio.
rank (r) · adapter
Rank r: the width of the bottleneck in ΔW = BA — how many directions of change you buy; small r trains fewer numbers but expresses less. Adapter: the saved, mergeable artifact of adaptation (here: the LoRA delta, submitted per the multi-LoRA layout).
quantization · NF4 · QAT · W4A16 S24
Quantization: storing/computing numbers at lower precision than 16/32-bit floats to save memory. NF4: QLoRA's 4-bit NormalFloat dtype, information-theoretically matched to normally distributed weights. QAT — quantization-aware training: training with simulated low-precision arithmetic so parameters learn to survive the later integer conversion. W4A16: weights 4-bit, activations 16-bit — the base model's serving format (hence “qat-w4a16” in its name). Teachable nuance: QAT happens before deployment (Google did it); QLoRA happens after, adapting an already-quantized model.
QLoRA S17
Backpropagating gradients through a frozen, 4-bit quantized base model into LoRA adapters — fine-tuning reaches 16-bit-quality results at a fraction of the memory (a 65B model on one 48 GB GPU). Here: the reason H6 fits the 4×L4 (96 GB) rig.
SFT — supervised fine-tuning
Training on demonstration sequences with the standard next-token loss, masked to the assistant's turns — “learn to behave like these transcripts.”
RFT — rejection-sampling fine-tuning S18
Sample many attempts per task, keep only the successes (rejection sampling), fine-tune on those. Here: H6's engine — resolved Config-3 trajectories are, by construction, doctrine-following trajectories. SWE-smith used RFT to reach 40.2% Pass@1 with SWE-agent-LM-32B.
Pass@1
The fraction of tasks solved by a single sampled attempt (versus Pass@k's best-of-k) — the metric SWE-bench leaderboards report and this competition's resolve rate mirrors.
GRPO — Group Relative Policy Optimization S19–S20
A reinforcement-learning algorithm (from DeepSeekMath) that samples a group of rollouts per prompt, computes each rollout's advantage as its reward standardized within the group, and optimizes the policy against that — dropping PPO's separate value network. Here: the plausible next-next lever (RL on resolve signal) once H6's SFT plateau lands; not scheduled this window.
catastrophic forgetting S21–S22
New-task training degrading old capabilities — for LoRA, updates interfering with the dominant singular directions that carry pretrained knowledge. Mitigations: replay data, regularization, orthogonal projection. Here: why H6 mixes general-instruction data and why P3 (the canary set within 2 pp) is a gate, not a nicety.

What would move the numbers

  • A harder task: read windows and subgraphs grow toward the 5k/10k caps; H2's savings grow with repo size while the fixed ladder's cost grows linearly — the tier gap widens.
  • Falsified mechanisms: any H that clears mechanism endpoints but not task-level resolve redirects effort to H6-or-bust + the paper track (02-hypotheses §4) — a finding either way.
