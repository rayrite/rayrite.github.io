A beginner's guide to the v5 replay deck (httpx_3672)

Prepared 2026-10-27. A gentle companion to 03-bcf-simulation-httpx-3672.slides.v5.html, "naive vs BCF, replayed call by call". It follows the deck's 20 sections in order and explains every function the deck uses.

[V][REPLAY][SIM][EST][R]

#0. Read this first

#0.1 What the deck is

The deck compares three AI agents fixing the same real bug:

Agent Who it is Calls (total / charged) Result
Naive (Config 1) A generic agent: "here is the issue, fix it". 43 / 40 resolved = False
BCF (Config 3) The same model run under the Batonic Coding Framework's rules, notes and checklists. 30 / 28 resolved = True
Tier-2 (proposed) BCF plus the improvements the replay suggested. 22 / 20 resolved = True

"Replayed" is the key word. Every tool call in the deck was actually executed against a real copy of the project, through an emulator of the competition's tools. Every output you see on a call card is the real output. What is not real is the choice of which call to make next. Those choices were scripted by a person to match each agent's design; no AI model chose them.

So the deck answers: "if an agent made these choices, what would really happen?" It does not answer "what would Gemma actually do?" That needs live runs (§14 of the deck).

#0.2 The five evidence tags

Every claim in the deck carries a tag. Learn these first.

Tag Meaning How much to trust it
[V] verified Read straight from the competition data (task, code, graph, harness README). Fully. Anyone can re-check it.
[REPLAY] Produced by actually running the call in the emulator. High. Two parts are emulated from documentation rather than real source: the graph-tool name matcher and the BCF skill scripts.
[SIM] simulated Which call comes next. Scripted, not sampled from a model. Design intent only.
[EST] estimated Wall-clock minutes and model-token counts. Rough ranges.
[R] research Claims from published papers, numbered S1, S2, … in the deck's source list. As good as the cited paper.

#0.3 How to read a call card

Each call in Steps 1–8 is a card. Its ID tells you whose call it is: N for naive (N1–N43), C for BCF (C0–C29), T for Tier-2 (T0–T21). A card shows:

Part of the card What it tells you
The call itself The exact tool and arguments, e.g. read_file("src/httpx/_parsers.py", 370, 425).
Real output (click to expand) What the tool really returned.
Budget meter (7/50 or free) How many of the 50 charged calls have been used after this one.
Shadow verdict (PASS if submitted / fail if submitted) If the agent had submitted right now, would the grader have passed it? The replay computed this after every call by running the grader on the current code. The real harness doesn't offer this; it is a teaching instrument.
Issue-bullet probe (k/11) How many of 11 simple checks of the issue's five bullets the code currently satisfies (6 checks in the sync tree, 5 in the async tree). The real reference fix scores 10/11.
Gain pill How much the call actually helped: high gain, some gain, ≈ zero gain (repeats, empty answers, tests that couldn't fail) or negative (reverts).
How it was chosen The rule that picked this call.
Meant to buy / Actually bought What the call was supposed to achieve, and what it really achieved, judged from the real output.

Below each step's two columns there are three more blocks: "Where the improvement happens" (the step's verdict), ◆ teachable moments, and "The next-tier lens" (Tier-2's calls for that step).

#1. The 60-second picture

#1.1 The game

The Kaggle competition gives an AI model (Gemma 4, 31B) a real bug report from a real Python project. The model must fix the code by itself. It cannot type into an editor. It can only ask the harness (the competition software) to do things for it, one tool call at a time.

Think of it as an exam taken through a letterbox:

  • You slide a note under the door ("show me lines 370–425 of _parsers.py"), and a clerk slides back the result.
  • You get 50 charged notes. A couple of note types are free.
  • When you are done, you send a "submit" note, and the clerk photocopies every change you made (the patch).
  • A different examiner, in a different room, applies that photocopy to a fresh copy of the project, adds secret test questions, and runs them. All pass: score 1. Anything else: score 0.

#1.2 Words you need

Word Plain meaning
Agent The AI model plus its instructions.
Harness The competition software that runs the agent and its tool calls, and enforces the budget.
Tool call One request to the harness. Most cost 1 of the 50; get_status and submit_patch are free.
Turn One response from the model, which may contain several tool calls. The deck counts calls, not turns.
Container A The sandbox where the agent works: an isolated Linux box with the project at /workspace.
Container B A fresh sandbox used only for grading. The agent never sees it.
Patch The agent's changes as a git diff. The only thing carried from A to B.
test_patch The hidden test changes the grader adds in Container B.
resolved True if the hidden tests all pass in Container B. This is the whole score.

#1.3 The flow

 Container A (agent works here)                    Container B (grader; agent never sees it)
 ┌──────────────────────────────────┐              ┌────────────────────────────────────────────┐
 │ /workspace = repo at base commit │              │ fresh repo at base commit                  │
 │                                  │              │ 1. apply agent's patch                     │
 │ agent ⇄ tools (50-call budget)   │   patch      │ 2. RESET any test files the agent touched  │
 │ ... edits files ...              │ ───────────► │ 3. apply hidden test_patch                 │
 │ submit_patch()  →  git diff      │              │ 4. run pytest tests/test_parsers.py        │
 └──────────────────────────────────┘              │ 5. exit code 0 and all pass → resolved     │
                                                   └────────────────────────────────────────────┘

#2. The task and its six traps (deck §3)

Deck §3 →

#2.1 The issue

This is the entire problem statement, 243 characters:

Server connection handling.

  • Add HTTPParser.keep_alive.
  • Server... always read request to completion on keep alives.
  • HTTPParser.complete -> .reset
  • Close streams on server exit.
  • Don't raise KeyboardException on server exit.

That is five requests, with no error message, no traceback, no example and no file names. Two names in it are slightly wrong:

  • The real fix adds is_keepalive(), not keep_alive.
  • Python's exception is KeyboardInterrupt; KeyboardException doesn't exist.

The one clear, mechanical instruction is "rename HTTPParser.complete to reset".

#2.2 What is graded

The hidden test_patch changes one file, tests/test_parsers.py, replacing p.complete() with p.reset() five times. The grader then runs that file's 24 tests. The reference fix (the gold patch) touches 7 files, but the score only checks that httpx.HTTPParser.reset() exists and works. Probe X1 proved that renaming one method in one file is enough to pass.

#2.3 The six traps

Trap What it is Why it hurts
1. Visible tests contradict the graded tests The agent's copy of tests/test_parsers.py still calls p.complete() (lines 70, 116, 318, 557, 594). The correct rename turns the agent's local tests red. It looks broken but isn't.
2. Two trees The project has an async copy (src/ahttpx/) and a sync copy (src/httpx/) of the library. Fixes must land in both, and grep shows every hit twice.
3. A silent bug at the caller _server.py:92 says self._parser.complete with no parentheses. The method is looked up and thrown away, never called. No test reaches it.
4. Ungraded bullets Response(code=500…) raises a TypeError; _streams = list[NetworkStream] stores a type, not a list; wait() lets Ctrl-C escape. Real bugs that the score never sees.
5. The sync tree is generated (new in v5) scripts/unasync writes 15 of the 16 src/httpx/*.py files from src/ahttpx/ by deleting async/await. Nothing marks them as generated. Hand-edits to src/httpx/ are erased the next time someone runs the generator.
6. The graph is blind (new in v5) The organizers' code graph indexes no async def and has no real caller edges. Graph tools can't find the async tree's methods or who calls complete.

Trap 3 has a twist the deck shows in code. In the async source the same line is await self._parser.complete, which crashes (TypeError: object method can't be used in 'await' expression, probe X7). The generator deleted await, which turned a crash into a silent no-op in the sync copy.

#4. The decision engines (deck §5)

Deck §5 →

The deck uses some formal vocabulary. Here it is in plain words.

Term Plain meaning
POMDP "Acting when you can only see clues, not the truth." The agent can't see which code is wrong or what the hidden tests check; each tool output is a partial clue.
Belief state What the agent currently thinks is true. BCF writes its beliefs down (spec and journal). Naive's exist only in its context window.
Policy The rule that decides the next tool call.
Heuristic A good-enough rule used because the perfect one can't be computed. In the deck this is a compliment.

The three agents run three policies:

Naive BCF Tier-2
How it picks the next call Reacts to the latest output: red test → read the test → undo. Asks five questions in order (below). Same five questions, with sharper versions of Q2 and Q5.
Where its beliefs live Context window only. Spec plus journal on disk. Spec, journal and a belief log.
When it stops Budget pressure plus a green local suite. When every gate check passes. Same as BCF.
Cost on this task 40 charged, 7 repeats, 2 reverts 28 charged, 0 reverts 20 charged, 0 reverts

BCF's five questions, asked before every call:

  1. Which phase am I in? Spec, localize, patch or validate. Each phase allows certain tools.
  2. What is my next unmet obligation? The next unconfirmed hypothesis, the next bug in the fix order, or the next check.
  3. Can I afford it? At most 10 calls to localize; submit by call 42; rescue after 3 failed checks or 25% of the budget.
  4. Have I tried this and failed? Look it up in the journal; never repeat a failed action.
  5. Is there a cheaper tool for the same question? Graph, then grep, then read, smallest window first.

What Tier-2 changes:

  • Q5 ranks calls by p/C: the chance the call finds the answer, divided by its cost. Plain BCF looks at cost only.
  • Q2's checklist gains two obligations: provenance ("is this file generated?") and closure ("is every old name gone?").
  • Every red test first passes through an asymmetry detector: "was this failure predicted by the spec?"
  • Commands are shaped so the important lines survive the 5,000-character output cap.

#5.1 get_status(): read the meters

What it does. It returns the budget state as a small JSON message and doesn't touch any file. This is the real output from card C0:

{"status": "ok", "tool_calls_used": 0, "patch_submitted": false, "patch_size": 0,
 "tool_calls_remaining": 50, "max_tool_calls": 50, "max_time_minutes": 60.0,
 "max_turns": 500, "command_timeout_seconds": 300}

What code is inside. The harness's own source (swegemma/tools/execution.py) is not available. From its documented contract (HARNESS_README §6.1) it is almost certainly a few lines that read counters the harness already keeps. illustrative:

@budget_gated(count_tool_call=False)      # False = this tool is free
def get_status() -> str:
    return json.dumps({
        "status": "ok",
        "tool_calls_used": ctx.tool_calls_used,
        "patch_submitted": ctx.patch_submitted,
        "tool_calls_remaining": ctx.budget.tool_calls - ctx.tool_calls_used,
        "max_tool_calls": ctx.budget.tool_calls,
        ...  # time and turn limits
    })

@budget_gated is the harness's toll booth, and every tool passes through it:

  • When count_tool_call=True, it adds 1 to tool_calls_used.
  • Once 10 or fewer charged calls remain, it adds a budget_warning field to every response. You can see the real warning on card N42: "Only 10 tool call(s) remaining (40/50 used)".

The replay emulator does exactly this in replay.py, lines 71–98.

Why it is "free" but not worthless. It costs no budget, but it costs a little time and context. The deck's Step 1 lesson is that its information gain was zero too, because the starting prompt already states the budget.

N1 versus C0. Both are the same free call. In this deck both cards say free, and the budget meter stays at 0 for both. N, C and T simply number each agent's calls (naive starts at 1, BCF and Tier-2 at 0). The difference is only why each agent made the call: naive out of habit, BCF as step one of its protocol.

#5.2 run_command(command): run a shell command

What it does. It runs any Linux command in /workspace, such as grep, pytest, sed, git diff or python.

What it returns. The printed output, cut at 5,000 characters each for stdout and stderr, plus the exit code. Exit code 0 gives "status": "ok"; anything else gives "status": "error".

Limits. 300 seconds per command, and no internet.

Lessons in the deck:

  • The output cap can hide the verdict (N9). pytest prints tracebacks first and its summary last. At N9 the line "5 failed, 19 passed" was cut off, so the agent judged a 24-test suite from two and a half tracebacks. Tier-2 uses pytest -q --tb=line -rf … | tail -9 (T19) so the summary survives. This idea is hypothesis H3, "evidence shaping".
  • One command can replace many edits (C13). BCF renamed _complete → _reset in four pool and server files with one sed, instead of eight edit_file calls. It deliberately limited the sed to those four files: a repo-wide rename would also have hit HTTPStream._complete in _streams.py, an unrelated attribute with the same name (the "decoy" that N2's grep turned up).
  • It is the right way to write to /tmp. See 5.5.

#5.3 read_file(filepath, start_line, end_line): look at part of a file

What it does. It returns lines start_line..end_line of a file, counting from 1 with both ends included.

Limits. At most 150 lines and 10,000 characters per call. If either cap is hit, is_truncated: true says so.

In the deck:

  • Naive repeats itself. N5 and N7 re-read exactly what N4 and N6 had just read. Their output is byte-identical, so they have zero information gain by construction: if you can predict a result with certainty, it can't change your mind.
  • BCF reads wide and targeted. C6 reads _server.py 28–105 and finds line 92 (no parentheses), line 46 (Response(code=500…)) and wait() at line 100. C7 reads _network.py 75–190.
  • C8 exists because edits need the exact text. edit_file needs the exact text it is replacing, so you must read a region before editing it. The earlier v4 trajectory edited _parsers.py without ever reading it, which is impossible.

#5.4 edit_file(filepath, old_string, new_string, allow_multiple=False): find and replace

What it does. It finds old_string in the file and replaces it with new_string. That is one find-and-replace per call.

Matching. It tries an exact match first, then whitespace-tolerant matching.

Safety. If old_string appears more than once and allow_multiple is False, nothing changes. If the text isn't found, it fails loudly with FileEditError. That failure is a free safety net: a wrong guess costs one call and does no damage (see C11).

In the deck:

  • N8 renames the method, and the shadow verdict turns PASS.
  • N13 renames it back, and the verdict turns fail for good.
  • C9–C12 rename in both parsers. Each parser needs 2 calls, because the rename and the return True line are far apart.
  • C25 uses allow_multiple=True to change all five p.complete() lines in the test file in one call.
  • Because each call makes exactly one replacement, BCF honestly needs 30 calls here, not v4's 24 (errata, §17).

#5.5 write_file(filepath, content): create or overwrite a file

What it does. It writes a whole file at /workspace/<filepath>.

The trap. A leading / is stripped, so write_file("/tmp/repro_reset.py") actually creates /workspace/tmp/repro_reset.py. submit_patch then ships that file inside the patch (probe X5). The earlier v4 trajectory made exactly this mistake.

In the deck. v5 avoids write_file entirely. C24 and T18 write the repro script with run_command and a heredoc:

cat > /tmp/repro_reset.py <<'EOF'
...script...
EOF
python /tmp/repro_reset.py

#5.6 The three graph tools (C3, C4, C5)

Before the competition, the organizers turned the httpx code into a graph:

  • 740 nodes, one per function or class, named like httpx._parsers.HTTPParser.complete.
  • 1,618 edges, all labeled calls.
  • An embedding for each node: a list of 256 numbers summarising the code, used to measure similarity.

Here is what each graph tool really returned in the replay:

Card Call Hoped for Real output
C3 search_similar_code("HTTPParser") Both trees' parsers. Itself, two HTTPConnection nodes and 7 test functions. All scores were 0.9968–1.0, and the async parser was absent.
C4 get_code_subgraph([4 classes from both trees]) The mirror structure. 4 nodes and 0 edges. The only "mirror" information was the list of names the agent typed in.
C5 get_code_neighbors("httpx._parsers.HTTPParser.complete") Who calls complete. One neighbour, the parent class: a containment edge stored as a calls edge.

Each tool in plain words:

  • search_similar_code(query, k=10) looks up the node named query and returns the k nodes whose number-lists point the same way. Lesson: when every score is about 0.997, the ranking means almost nothing. Always look at the spread of scores, not just their order.
  • get_code_subgraph(nodes) returns those nodes plus the edges between them (an "induced subgraph").
  • get_code_neighbors(node) returns every node with an edge to or from node.

Why they failed here. The graph has two blind spots, which are Trap 6:

  • It indexes no async def, so two-thirds of the async parser is invisible.
  • It has no cross-file caller edges.

That makes it a symbol index ("does this name exist?"), not a caller map ("who calls this?").

Where the twin-tree knowledge really came from. The starting prompt includes a free workspace listing that shows src/ahttpx/ next to src/httpx/.

Tier-2 skips the graph. One word-bounded grep (T3) finds the rename sites and detects the generator, in one call. This is hypothesis H4, "search first".

#5.7 submit_patch(): hand in the work

What it does. It runs git add -N . (so new files are included) and then git diff, and stores the result as the patch. The session ends after the current model turn.

Cost. Free. It still works after the 50 charged calls are used up.

In the deck:

  • N43: 4 files, 2,851 bytes. Container B: 5 failed, so resolved = False. The graded tests call p.reset(), which this patch never defines.
  • C29: 8 files (7 library files plus the migrated test file), 10,768 bytes. Container B: 24 passed, so resolved = True.
  • T21: 7 files with no test edits. Container B: 24 passed, so resolved = True.

#5.8 run_skill_script(...): how BCF's helpers would run

A competition submission may include a skills/ folder. Each skill is a directory with:

  • SKILL.md: a short instruction sheet, and
  • optional Python scripts in scripts/.

run_skill_script is the tool that runs one of those scripts. It comes from Google's Agent Development Kit (ADK), not from the 9 harness tools. The competition overview says skill scripts run inside the same container and share files with run_command.

Two things are not yet known or are known hazards:

  • Budget cost is unverified. Nobody has confirmed whether a skill-script call costs one of the 50. The deck lists this as data item D18 (a one-off probe). The replay assumes it is charged.
  • A crash bug exists. Forum reports show that passing the script's file_path as a list instead of a string ends the task (3.4% of skills-based runs).

#5.9 classify_issue (C1, T1): what kind of problem is this?

This is a BCF proposal, not an existing script. It is plain Python, not an AI call. It reads only the issue text and picks a plan template. The emulator (replay.py, lines 206–218) is about 15 lines of keyword rules:

Rule Signal
A bullet starts with "Add", "Support" or "Implement" Feature
A bullet contains "->" or "rename" Refactor
A bullet says "always", "never", "close" or "don't" Behavior
The text contains "Traceback (most recent call last)" Traceback

Its real output on card C1:

  • Route: compat_or_refactor + feature sub-spec.
  • Signals: 1 feature, 1 refactor, 3 behavior; no traceback and no "expected/got".
  • Anchors: HTTPParser, KeyboardException, complete, keep_alive, reset.

Why issue text only? The issue is the only thing guaranteed to describe what is graded. The visible tests are stale (Trap 1), and the code is wrong by definition. The research term for code that satisfies the visible tests but not the specification is test overfitting.

Gate G0. BCF's rules say file tools stay locked until the spec is valid. In this competition a submission is configuration only (YAML) and can't intercept tool calls. So "locked" means either:

  • the prompt says so, or
  • the planning sub-agent is simply not given file tools.

#5.10 write_spec (C2, T2): write the plan down before looking

This is also a BCF proposal, a skill script that checks the plan's shape. The plan lists five hypotheses:

ID Hypothesis Target Depends on
B1 Rename complete → reset (returning True/False), both trees httpx._parsers.HTTPParser.complete n/a
B2 Add is_keepalive() httpx._parsers.HTTPParser B1
B3 The server never resets the parser (no parentheses) and never drains the request httpx._server.HTTPConnection._complete B1, B2
B4 _streams holds a type, and streams are never closed httpx._network.NetworkServer.__init__ n/a
B5 wait() leaks Ctrl-C; Response(code=500) raises a TypeError httpx._server.HTTPServer.wait n/a

The plan also sets:

  • fix_order = [B1, B2, B3, B4, B5], a validation plan, and a budget plan.

The script checked three things: the schema is valid, the fix order respects the dependencies, and all five targets are real graph nodes. It returned "G0": "PASS - file tools unblocked".

Two ideas from the deck's Step 3:

  • Pre-registration. Scientists write their predictions down before seeing the data, so the data can prove them wrong instead of being reinterpreted. The spec does the same for a debugging run. When the tests go red after the rename, "was this predicted?" has a written answer: yes.
  • DAG and topological order. A DAG is a dependency diagram you can't go in circles in. A topological order is any order that respects "this before that". B3's code calls is_keepalive(), which B2 creates, which only makes sense after B1's rename. Writing B3 first would produce code that can't run, and it would look like a wrong hypothesis.

#5.11 The journal, the ratchet and the gates (BCF proposals)

  • Journal. A small text file in /tmp (outside the patch) with one line per important action. The key line, written at C9, is: t=09 … local suite WILL go red; expected — hidden tests renamed.
  • Ratchet. A ratchet only turns one way. BCF never undoes a justified edit because of a red test the spec predicted. Failures route forward (fix, check, rescue), never backward (revert).
  • Gates G0–G6. Yes/no checks computed by code, not judged by the model:
Gate Check
G0 The spec is valid.
G1 Only allowed files were changed.
G2 The patch applies cleanly.
G3 Every changed file still compiles.
G4 The target tests pass.
G5 Nearby tests still pass.
G6 The patch is not empty.

BCF submits only when all seven are true. The submission can't run code of its own, so the gates cost a charged run_command: C26 runs G4, C27 runs G5, and C28 runs G1–G3 and G6 together.

#6. The eight steps (deck §6–13)

Each step below covers what each agent does, the idea it teaches, and the card to look at. All outputs are real.

#Step 1: Orient

Deck →

What happens. N1, C0 and T0 are each a free get_status().

Lesson. Before every call, ask: "what could this result change about what I do next?" Here the honest answer is "nothing", because the prompt already stated the budget. That is acceptable only because the call is free.

Tier-2 adds. It also logs the serving environment (model, adapter and wheel versions), so the run can be interpreted later (D16).

#Step 2: Frame

Deck →

Naive (N2, N3). It runs grep -rn 'complete' src/ tests/ and gets 53 lines (3.6 kB):

  • 19 are real rename sites.
  • 12 are a decoy: HTTPStream._complete in _streams.py, an unrelated callback slot.
  • 22 are prose and comments ("complete URL").

N3 shrinks the list to 13 file names. The twin tree is now visible, but naive has nowhere to store "every fix must land twice".

Why naive reverts. It applies the regression heuristic: "tests were green before my edit and red after, so my edit is wrong". That rule is almost always right. #7. The research sections (deck §14–20)

#7.1 Statistics: one run proves very little (§14)

Deck →

The planned experiment is 30 tasks × 3 random seeds per configuration. The deck explains why that is a blunt instrument:

  • It can only reliably detect a difference of about 17 percentage points, or about 22 after correcting for testing 8 hypotheses.
  • Typical published improvements are 2–9 points.
  • Seeds are not extra tasks. Because the same task tends to behave the same way across seeds, 90 runs carry about as much information as 37 independent ones.
  • On the 58-task public leaderboard, scores of 0.20, 0.22 and 0.24 are just 12, 13 and 14 tasks, which is statistically indistinguishable.

What to do instead:

  • Use a paired t-test on the 30 per-task average differences.
  • Make mechanism measurements the main endpoints. Examples: "how often does the agent revert a spec-mandated edit?" and "how many calls to localize?". These give hundreds of data points per run, not 30.
  • Write the plan down before running (pre-registration).
  • Report a non-result as "couldn't detect effects smaller than ~17 points", never as "no effect".

One-line takeaway: one run gives one bit per task, so measure the mechanisms inside the run.

Tier In one phrase What it trusts This run

The order matters: discipline, then calibration, then competence. Train last, because training on a scaffold you are about to change wastes the run.

The deck is also honest about the score: Tier-2 doesn't change it on this task, since BCF already passes. Its value would show on large repositories, generated code and tight budgets.

#8. What the deck still leaves open

  • The decisions are scripted. The deck shows consequences, not what Gemma would choose. Probes X1 and X2 show a lucky naive run passes.
  • Two parts are emulated from documentation: the graph tools' name matcher, and the BCF skill scripts. D19 asks for a check against the live harness.
  • Whether skill scripts cost a call is unknown (D18). If they are free, BCF's and Tier-2's charged counts drop by 2.
  • Test-file edits may vanish. Under the newer wheelhouse v30 (forum intel, 2026-10-12), test-file edits are dropped from the patch, so BCF's patch would be 7 files, not 8. The score is unaffected.
  • Measurements came from Windows. Tool times were measured on Windows, not in the competition's 2-vCPU container. One Windows-only test (test_multipart) is skipped in full-suite runs.

The bottom line for a beginner: the replay keeps the deck's core lesson and changes the details.

  • The lesson: write the plan and your reasons down before acting; trust a clear instruction over a misleading local signal; never undo a justified fix in a panic.
  • The details: the graph tools didn't do the detective work (grep and short reads did), honest accounting costs more calls, and the next tier comes from measuring, not from more rules.
