Deep dive: how classify_issue and write_spec would really work

Prepared 2026-10-27. Companion to the v5 replay deck (cards C1, C2, T1, T2) and to the beginner guide. It turns BCF's two proposed spec helpers into a concrete design, tests a working prototype on the real httpx_3672 snapshot and on all 129 training tasks, and ends with an honest estimate of how likely the deck's scenario is in real runs.

[V][REPLAY][SIM][EST][R]

#0. The short version

What they are. Both helpers run at the start of a BCF run, before the agent reads any code:

  • classify_issue decides what kind of problem the issue describes, and checks the issue's names against the repository.
  • write_spec checks the agent's written plan and turns it into a checklist.

Neither exists in the competition harness. In the deck they are emulated.

How I'd build them. One small, standard-library-only Python file, bcf.py:

  • It is installed once per task into <repo>/.git/bcf/, where git diff never looks.
  • After that it is driven by ordinary run_command calls, with the input passed through a heredoc.
  • Only the one-time install goes through the ADK skill tool, with no arguments. Everything else avoids the known hazards of passing data through skill-tool arguments.

A working prototype is at scratch/bcf_skill_proto/bcf.py. Its installer, install.py, is written but has not been tested inside the real harness.

What the prototype does on httpx_3672 [PROTO]:

Helper What it produced
classify_issue Routed the issue as a refactor and found both copies of complete. Predicted the exact 5 visible test lines that the rename turns red (lines 70, 116, 318, 557, 594). Detected the unasync generator and its 15 generated files.
write_spec Validated the plan and derived the fix order. Pointed one edit at the async source file instead of the generated copy. Rejected a dependency cycle, a made-up symbol and a vague plan, each with a specific message. Accepted a fenced JSON block with a trailing comma.

Every call returned under 1.6 kB of output. Classification took 0.6–3.2 s and spec validation 0.4–1.0 s, measured on Windows across six runs. Nothing it saved appeared in the patch.

What the 129 training tasks say [MEASURED]:

  • The issue style that drives the deck's classification (a bulleted list with an old -> new arrow) appears in one task out of 129: httpx_3672 itself. A rule-based router built from this task would not generalize. Routing should be the model's job; the script should do what code is good at: checking names against the repository and predicting which tests will go red.
  • The deck's decisive trap, a correct fix that turns the visible tests red, appears in its strict form in about 1 to 4 of the 129 tasks (≈1–3%).

How likely is the deck's scenario? As a mechanism, real but rare. As a trajectory, essentially never as written. As an outcome, the naive agent fails this task maybe 40–65% of the time, not always. Section 11 gives the full answer.

#1. Where the two helpers sit in a BCF run

 Phase 0  setup       run_skill_script(bcf-spec install)       copies bcf.py into .git/bcf/   (1 call, cost unverified)
 Phase 1  spec        run_command: bcf.py classify <<EOF        route + anchors + expected red (1 charged call)
                      run_command: bcf.py spec     <<EOF        validate, fix order, checklist (1 charged call)
                      planner's final text → session.state["bcf_spec"]  (pinned into the solver's instruction)
 Phase 2  localize    read_file / grep, guided by the checklist
 Phase 3  patch       edits in fix_order; journal lines appended with run_command
 Phase 4  validate    gates G1–G6; submit only when all are true

In the deck, Phase 1 corresponds to cards C1 (classify_issue) and C2 (write_spec), and to T1 and T2 for Tier-2. The deck charges each one call.

#2. What the real harness allows, and what that forces

Before designing anything, here is what the competition harness and its users have established. Each fact constrains the design.

Fact Source What it forces
Submissions are declarative YAML. Custom Python can only ship as skill scripts. HARNESS_README §2.1; Kaggle overview The helpers must be skill scripts. There is no orchestrator that can run them automatically.
run_skill_script takes its script arguments as an array (args). On the scorer's vLLM 0.19.1, a malformed array argument can hang the tool-call parser; about 10% of malformed arrays did in a fuzz test. Forum 746336 Never pass the issue text or the spec through args.
Passing file_path as a list instead of a string ends the task (3.4% of skills-based runs). Forum intel, 2026-10-02 Call run_skill_script as rarely as possible, with no arguments.

Whether a skill-script call is charged against the 50 is unverified. Deck data item D18 Prefer run_command, whose cost (1) is known.

The task graph indexes no async def, and the graph files may not be inside the sandbox. Replay (Trap 6); council notes C6 Resolve names with Python's own ast module over the repository, not with the graph.

#3. The architecture

#3.1 Files in the submission

submission/
├── agent.yaml                      # SequentialAgent: bcf_plan → solver
├── sub_agents/
│   ├── bcf_plan.yaml               # LlmAgent, output_key: bcf_spec
│   └── solver.yaml                 # LlmAgent, instruction includes {bcf_spec}
├── prompts/
│   ├── bcf_plan.md
│   └── solver.md
└── skills/
    └── bcf-spec/
        ├── SKILL.md                # when and how to use the helper
        └── scripts/
            ├── install.py          # copies bcf.py into <repo>/.git/bcf/ (no arguments)
            └── bcf.py              # classify + spec (stdlib only)

#3.2 The agent wiring (illustrative)

Field names follow HARNESS_README §2.3. Exact skill-tool argument names must be copied from the installed adk-submission wheel.

# agent.yaml
agent_class: SequentialAgent
name: bcf_root
sub_agents:
  - config_path: sub_agents/bcf_plan.yaml
  - config_path: sub_agents/solver.yaml

# sub_agents/bcf_plan.yaml
name: bcf_plan
model: gemma-4-31b-it-qat-w4a16-ct
instruction: !include ../prompts/bcf_plan.md   # contains {problem_description}
tools: [run_command, read_file, edit_file, write_file, get_status, submit_patch,
        search_similar_code, get_code_neighbors, get_code_subgraph]   # same list as solver: unknown tools are fatal
skills: [skills/bcf-spec]
output_key: bcf_spec        # the planner's final text is saved to session state

The solver's prompt then starts with a block that the model sees on every turn:

## Your validated plan (from the planning step; do not re-derive it)
{bcf_spec}

#3.3 How "Gate 0" really works here

The deck describes Gate 0 as file tools "locked until the spec is valid". In this harness, a hard lock is neither possible nor safe (§2). The design keeps the intent with three softer but real mechanisms:

  1. Structure. The planner sub-agent always runs first, and its instruction asks only for the three helper calls.
  2. Feedback. bcf.py spec answers "G0": "FAIL" with specific errors until the plan is valid.
  3. Pinning. The planner's summary becomes part of the solver's instruction, so the plan survives context compaction. That is hypothesis H10's "pinned state" for free.

#3.4 The three calls, exactly as the model would make them

# 1. setup (once; no arguments, so no array hazard)
run_skill_script(skill = "bcf-spec", file_path = "scripts/install.py")

# 2. classify_issue
run_command("""python3 .git/bcf/bcf.py classify <<'EOF'
<the issue text, copied from the instruction>
EOF""")

# 3. write_spec
run_command("""python3 .git/bcf/bcf.py spec <<'EOF'
{"task_class": "compat_or_refactor", "bugs": [ ... ]}
EOF""")

The quoted <<'EOF' matters: the shell then passes the text through untouched, so quotes, backticks and $ signs in the issue or the JSON need no escaping. If the setup call is skipped, call 2 fails with "No such file", and the planner can recover by running the setup.

#4. classify_issue in depth

#4.1 What goes in, what comes out

Input: the issue text on standard input.

Output: one JSON object, also saved to .git/bcf/classify.json.

Field Meaning
route The plan template: bugfix, feature or compat_or_refactor, plus + multi when several kinds of bullet are present.
signals Which bullets read as feature, refactor or behavior; whether there is a traceback or an "expected … got" pair.
renames Every `old` -> `new` pair, with the new name fully qualified.
anchors_resolved Issue names that exist in the repository, with their full dotted names (both trees).
anchors_missing Issue names that don't exist, with the closest real names (including Python builtins).
expected_red The Trap-1 predictor. For each rename, every visible test line that uses the old name, with the prediction that those tests will fail and that this is expected.
generators Code-generator scripts found in scripts/, tools/ or bin/, with their source → output folder pairs and the exact files they generate.
next One line telling the model what to do next.

#4.2 The algorithm, step by step

  1. Split into bullets (lines starting with * or -).
  2. Read the signals.
    • A bullet starting "Add/Support/Implement/Allow/Introduce" is a feature signal.
    • A bullet containing "->", "rename" or "deprecat…" is a refactor signal.
    • "always/never/close/don't/should/must" is a behavior signal.
    • Separately, look for a Python traceback and an "expected … got" pair.
  3. Route. A traceback or an expected/got pair means bugfix. Otherwise a refactor signal means compat_or_refactor, a feature signal means feature, and anything else falls back to bugfix.
  4. Collect anchors: back-ticked names and CamelCase names such as exception classes.
  5. Parse renames: `HTTPParser.complete` -> `.reset` becomes HTTPParser.complete → HTTPParser.reset.
  6. Index the repository with Python's ast module. This records every class, def and async def with its dotted name, file and line. It is the index the task graph should have been: it sees the async tree.
  7. Resolve anchors: exact match first, then suffix match (HTTPParser.complete finds both httpx.… and ahttpx.…), then close matches for misspellings. Rename targets are skipped, because they are not supposed to exist yet.
  8. Predict expected red. For each rename, word-search the test folders for the old name. Each hit is a test that the correct fix will turn red.
  9. Detect generators. Look for unasync or "do not edit / auto-generated" markers, then read which files the script actually lists.

What a beginner should notice:

  • expected_red is the line that saves the run. In the deck, the BCF agent wrote "local suite WILL go red; expected" at C9, out of its own understanding. Here a script computes it before any code is read, down to the exact five line numbers in the hidden test patch. The model no longer has to be insightful at the critical moment; it only has to read its checklist.
  • Both trees are found from one name, because the index includes async def. That is exactly what the graph tools failed to do at C3–C5.
  • The generator and its file list are found before the first edit. That is Tier-2's provenance question (H6), answered in the same call.
  • Misnamed builtins get a suggestion (KeyboardException → KeyboardInterrupt). keep_alive gets none, correctly, because the method it describes doesn't exist yet.

#4.4 What it cannot do, and the corpus result that matters most

classify_issue's routing rules come from this one issue. Run over all 129 training tasks, they behave like this [MEASURED]:

Route Tasks How it got there
bugfix 68 An expected/got pair, or simply the default. No issue in the corpus contains a Python traceback.
feature (from prose words like "add" or "support") 59 Only a loose keyword fallback
feature (from a bullet) 1 The bullet rule
compat_or_refactor 1 The arrow rule: httpx_3672 only

The `old` -> `new` arrow occurs in 1 of 129 issues. Most issues are prose:

  • 37 have any bulleted list and 18 have a code block.
  • None has a traceback.
  • Length ranges from 42 to 10,095 characters (median 418). So the rule-based router was fitted to the deck's task. Its routing is close to a guess on everything else.

Recommended split of responsibilities:

  • The model routes. Reading prose is what a language model does well, and BCF's Tier-2 already proposes three drafts with a vote (H9).
  • The script measures. Resolving names against the repository, predicting expected-red tests and detecting generators are deterministic, cheap and testable, and that is where the prototype's real value showed. The script should accept the model's anchors and renames directly (for example bcf.py classify --rename HTTPParser.complete=reset), so long issues never have to be copied into a heredoc.

#5. write_spec in depth

#5.1 The spec the model writes

Field Required Meaning
task_class Yes One of bugfix, feature, compat_or_refactor, multi.
bugs[] Yes, 1–6 One entry per sub-problem the agent will address.
bugs[].id Yes A short, unique id such as B1.
bugs[].hypothesis Yes, ≥ 20 characters The code-level cause, not the symptom.
bugs[].target_symbol Yes A dotted name that must resolve in the repository (exempt when the fix shape is new_code).
bugs[].fix_shape Yes One of delete, replace, guard_add, check_add, iterator_or_logic_rewrite, new_code, other.
bugs[].depends_on No Ids that must be fixed first.
validation_plan No Repro location and tests to run.
budget_plan No Defaults: localize in ≤ 10 calls, force-submit at 42 used, rescue after 3 failed G4 checks or 25% of the budget without progress.

This is a simplified form of the BCF compendium's schema (§A6.3). The main differences:

  • target_symbol is a single string.
  • fix_order is not written by the model. It is derived from depends_on, so the model can't write an order that contradicts its own dependencies.

#5.2 What the validator does

  1. Parse leniently. It strips a surrounding Markdown code fence and trailing commas, two very common small-model JSON mistakes.
  2. Check every field against the table above.
  3. Check dependencies. Unknown ids are errors, and a cycle is an error that names the bugs involved.
  4. Derive fix_order by topological sort, stable in the order the bugs were written.
  5. Resolve every target_symbol against the ast index. If a name isn't found, it suggests close matches.
  6. Redirect generated targets. If a target's file is one the generator writes, the obligation points to the same symbol in the source file, with its real line number, and a note: "edit the source, then regenerate".
  7. Build the closure map. For every rename, it lists every code line in src/ that still uses the old name, grouped by file. The rule: every site must be renamed or explicitly classified as unrelated.
  8. Carry over expected_red from the classify step.
  9. Save the full result to .git/bcf/spec.json, and seed .git/bcf/journal.md with the fix order and the expected-red lines.
  10. Print a compact summary. Errors exit with code 1, so run_command reports "status": "error" and the model sees a clear failure.

#6. Cost and benefit

Option Charged calls Hazards Verdict
Recommended: install once, then bcf.py via run_command heredocs 2 (+1 setup, cost unverified) The setup call itself; copying a long issue into a heredoc Best balance
Each helper as its own run_skill_script call with args 2 (cost unverified) Array-argument parser hang; list file_path crash; scripts start in a temporary folder Avoid

No scripts: routing and spec rules only in the prompt 0 No validation, no name resolution, no expected-red prediction Cheapest, weakest

What the two calls buy, measured on this task:

  • The expected-red prediction removes the single decision the naive agent got wrong.
  • Name resolution across both trees replaces the three graph calls (C3–C5) that bought nothing.
  • Generator detection delivers Tier-2's 11th bullet.
  • A validated, pinned plan survives compaction.

#7. Failure modes and what to do about them

Failure How likely Mitigation
The model skips the setup call Medium in a single-agent design; low with a separate first step (47/48) SequentialAgent first step; classify fails loudly and the model can install
The model copies the issue text badly Low for short issues; rises with long ones Hybrid mode: pass anchors and renames, not the whole issue
Invalid JSON in the spec Medium for a 4-bit 31B model Lenient parser; specific errors; bounded retries (at most 2), then continue with the best valid spec
Misroute (wrong template) High with the rule router outside this task (§4.4) The model routes, with H9's 3-draft vote; the script reports evidence only
A hallucinated target symbol Medium Resolution check with close-match suggestions
Expected-red false positives (a common name like run matches many tests) Medium on large repos Report counts per file and cap the list; treat it as evidence, not a command
Expected-red misses (tests break for reasons other than a rename) High in general It only covers the rename form of Trap 1; other forms need H1's failure-signature rules
Slow indexing on big repos Low (about 1–2 s here; fastapi is larger) Cache the index in .git/bcf/
Output over 5,000 characters Low Compact summary; full result on disk
The planner's final text isn't saved to state Unknown Verify output_key behavior under SequentialAgent in the first local run

#8. How to test them before spending GPU time

  1. Unit tests (offline, no model): the prototype's runner run_proto.py already covers a valid spec and four bad ones. Extend it with a case per failure mode in §7.
  2. Corpus sweep over the 129 training tasks (corpus_stats.py):
    • routing accuracy against hand labels;
    • anchor-resolution precision;
    • expected-red recall against tasks whose hidden test patch edits lines the gold patch breaks.
  3. Replay (the v5 harness): swap the emulated C1/C2 for the real script and rerun the shadow verdicts.
  4. Live A/B on the 30-task split, with the plan pinned versus not pinned, and log the deck's data items:
    • D5: spec artifacts;
    • D8: asymmetry events;
    • D10: provenance probes;
    • D18: whether skill calls are charged.

#10. What this means for BCF

  • Keep the two helpers, but reassign their jobs. The model reads and routes. The script resolves, predicts and validates.
  • The expected-red predictor is the most valuable single output, but it fires only when the issue names a rename, which is rare. Its general form is H1: a detector that labels a red test "expected by spec" from its failure signature.
  • Generator detection and two-tree name resolution are cheap and general. Any repository with generated or mirrored code benefits.
  • Pinning the plan into the solver's instruction is free. It is probably worth more than either helper, because it protects every later decision from compaction.

#11. How likely is the scenario the deck simulates?

This is an expert estimate, not a measurement. Every number below is [EST], with the reasoning shown so you can disagree with a specific step.

#11.1 Separate the question into four

The deck's scenario is really four claims:

  1. A task with this trap structure appears in scoring.
  2. A naive agent fails it the way the deck shows.
  3. A BCF agent succeeds the way the deck shows.
  4. The gap shows up on the leaderboard.

#11.2 Will a task like this be scored?

  • This exact task: no. httpx_3672 is a training task, and the scored tasks are different ones. A forum participant believes they come from private repositories; that is unconfirmed.
  • The async twin-tree parts (Traps 2, 5, 6): the host has said the private tasks touch no async def, so these are very unlikely to recur.
  • The core trap (a correct fix turns the visible tests red): about 1–3% of tasks, judging from the training set. On the 58-task public split that is roughly 0.5 to 2 tasks.

#11.3 Would a naive agent fail it the deck's way?

Step Estimate Reasoning
It makes the rename at all 60–85% It is the clearest instruction in the issue.
It then runs the visible tests 70–90% The harness prompt tells it to verify with tests.
On red, it reverts or abandons the rename 30–50% Small models under "tests failed" pressure often undo their last change. But updating tests after an API rename is also common coding-agent behavior, and aliasing is another way out.
On red, it migrates the tests or aliases instead 30–50% Either passes (probe X2; and test edits are dropped from the patch under wheelhouse v30).
Generic hazards end the run anyway 10–25% Failed edit_file calls (43% on 31B), context overflow that empties the patch (≈12% of sessions on v28), malformed tool calls

Overall: the naive agent fails this task roughly 40–65% of the time. That is a coin flip, not a certainty. The source document says the same: a lucky naive roll passes.

The exact 43-call trajectory: essentially 0%. Any specific sequence of 43 decisions is vanishingly unlikely. The deck shows a typical failure path, not a forecast.

One historical twist: under wheelhouse v28, editing a test file made the hidden test patch fail to apply. In that period the naive agent's "migrate the tests" escape would also have failed, and so would BCF's own C25 step. That trap is fixed in v30, where test-file edits are dropped from the patch.

#11.4 Would a BCF agent succeed the deck's way?

  • BCF doesn't exist yet as a running system. Everything in the deck's BCF column is scripted. Real success depends on the 4-bit 31B model following a multi-phase protocol for about 30 calls. Forum evidence says 31B skips simple "first do X" instructions most of the time unless the structure forces them.
  • If it is built as in §3 (forced first step, script-computed expected red, pinned plan), the decisive moment needs no insight, only reading. I'd put P(resolve this task | BCF built well) at 55–80%. The root fix is a one-line rename, and the plan names it.
  • The clean 30-call, zero-revert run: about 5–20%. Failed edits alone will add calls. The budget probably still holds: the scoring script's default is 100 calls unless the submission's eval_config.yaml sets fewer.

#11.5 Would it show on the leaderboard?

  • The leaders resolve 14 of 58 tasks (0.24). The median team resolves about 5.
  • If the trap appears on 0.5–2 public tasks, fixing it is worth at most about 0–2 tasks (0–3 points).
  • The deck's own statistics section says 30 tasks × 3 seeds can only detect differences of about 17 points.
  • A close analog exists: robust-edit removed a whole class of wasted calls but left the resolved count unchanged (6/16 in every run).

Overall: expect +0 to +2 public tasks from this specific mechanism. Most of that comes from cheap general pieces (plan pinning, two-tree name resolution, compact test output), not from the rename predictor.
