### Algorithm (Python, ~80 LoC)
```python
import re, json
DIFF_FILE_HEADER = re.compile(r'^diff --git a/(\S+) b/', re.MULTILINE)
DIFF_PLUS_LINE = re.compile(r'^\+(?!\+)', re.MULTILINE)
TEST_FN_PATTERN = re.compile(r'^\+def (test_\w+)', re.MULTILINE)

for task in read_jsonl('tasks.jsonl'):
    patch = task['patch']
    test_patch = task['test_patch']
    rec_m4 = {
        'task_id': task['instance_id'],
        'm4': {
            'final_files_changed': DIFF_FILE_HEADER.findall(patch),
            'final_patch_chars': len(patch),
            'final_added_lines': sum(1 for line in patch.splitlines()
                                      if line.startswith('+') and not line.startswith('+++')),
            'tree_dirty_at_end': bool(patch.strip()),

    }
    rec_m5 = {
        'task_id': task['instance_id'],
        'm5': {
            'target_test_vector': TEST_FN_PATTERN.findall(test_patch),

        }
    }
```

## 4. Phase 2 — Graph & Embedding Probe (study only, no wish-list fields)

### Goal
Verify the existence and structure of per-task graph + embedding assets. No wish-list fields map directly to these, but the probe informs Phase 4 budget and resolves U4.

### Inputs
- `graphs/<instance_id>.json` — 127 files
- `embeddings/<instance_id>.npz` — 127 files
- `embeddings/<instance_id>.json` — 127 sidecars

### Outputs
- `graph_audit.jsonl` — 127 records: `{task_id, node_count, edge_count, has_file_paths, sample_node_name}`
- `embedding_audit.jsonl` — 127 records: `{task_id, vector_dim, vector_count, dtype, l2_norm_median, cosine_sim_p99}`
- `graph_embedding_report.md` — coverage table + cosine-sim histogram (verifies F4)

### Algorithm (Python, ~100 LoC)
```python
import zipfile, json
import numpy as np

for task_id in known_task_ids():
    graph_path = f'graphs/{task_id}.json'
    embed_path = f'embeddings/{task_id}.npz'
    graph = json.loads(zf.read(graph_path))
    npz = np.load(io.BytesIO(zf.read(embed_path)))
    vectors = np.stack([npz[k] for k in npz.files])
    cos = vectors @ vectors.T / (np.linalg.norm(vectors, axis=1, keepdims=True) ** 2)
    rec_graph = {
        'task_id': task_id,
        'node_count': len(graph['nodes']),
        'edge_count': sum(len(g['links']) for g in graph.get('links', [])),  # or however edges are stored
        'has_file_paths': any('file' in n for n in graph['nodes']),
    }
    rec_embed = {
        'task_id': task_id,
        'vector_dim': vectors.shape[1],
        'vector_count': vectors.shape[0],
        'l2_norm_median': float(np.median(np.linalg.norm(vectors, axis=1))),
        'cosine_sim_p99': float(np.percentile(cos[np.triu_indices(len(cos), k=1)], 99)),
    }
```

### Gate criterion
- 127 graph audit records + 127 embedding audit records.
- `has_file_paths == false` for ≥ 95 % (confirming F4: graphs lack file paths).
- Cosine similarity median ≥ 0.95 (confirming the embeddings are near-degenerate).
- Report generated within 60 s.

## 1. Why this phase is the most valuable static extraction

## 8. The "what about non-`def test_*` tests" caveat

The regex `^\+def (test_\w+)` misses:
- `async def test_*` — also captured (since `^\+` matches the prefix)
- `@pytest.fixture` decorators preceding a `def test_*` — captured

import zipfile, io, json
import numpy as np
from pathlib import Path

ZIP_PATH = Path("D:/.../gemma-4-developer-agent.zip")
OUT_PATH = Path(__file__).parent / "embedding_audit.jsonl"

def main():
    with zipfile.ZipFile(ZIP_PATH) as zf, OUT_PATH.open("w", encoding="utf-8") as out:
        for name in sorted(zf.namelist()):
            if not name.startswith("embeddings/") or not name.endswith(".npz"):
                continue
            task_id = Path(name).stem
            with zf.open(name) as f:
                npz = np.load(io.BytesIO(f.read()))
            keys = list(npz.files)
            vectors = np.stack([npz[k] for k in keys])
            norms = np.linalg.norm(vectors, axis=1)
            cos = vectors @ vectors.T / np.outer(norms, norms)
            upper = cos[np.triu_indices(len(cos), k=1)]
            rec = {
                "task_id": task_id,
                "vector_dim": vectors.shape[1],
                "vector_count": vectors.shape[0],
                "dtype": str(vectors.dtype),
                "l2_norm_median": float(np.median(norms)),
                "cosine_sim_p99": float(np.percentile(upper, 99)),
            }
            out.write(json.dumps(rec) + "\n")
```

# extract_m6_configs.py
import json, re, zipfile
from pathlib import Path

ZIP_PATH = Path("D:/.../gemma-4-developer-agent.zip")
OUT_PATH = Path(__file__).parent / "m6_static_records.jsonl"

def parse_simple_yaml(text):
    """Minimal YAML parser sufficient for these 4 files.
    Handles `key: value` and `key:` followed by indented subkeys."""
    result = {}
    stack = [(0, result)]
    for line in text.splitlines():
        if not line.strip() or line.lstrip().startswith("#"):
            continue
        indent = len(line) - len(line.lstrip())
        while stack and stack[-1][0] >= indent:
            stack.pop()
        parent = stack[-1][1]
        m = re.match(r'^(\s*)([\w_-]+)\s*:\s*(.+)?$', line)
        if not m:
            continue
        key = m.group(2)
        val = m.group(3)
        if val is None or val.strip() == "":
            parent[key] = {}
            stack.append((indent, parent[key]))
        else:
            # Strip surrounding quotes
            val = val.strip().strip('"').strip("'")
            try:
                parent[key] = int(val)
            except ValueError:
                parent[key] = val
    return result

def main():
    cfg = {
        "compaction_interval_effective": "unknown",
        "docker_image_name": None,
        "model_adapter_set": None,
        "thinking_budget_effective": None,
    }

    with zipfile.ZipFile(ZIP_PATH) as zf:
        # M6.6: eval_config.yaml (compaction not present)
        try:
            eval_text = zf.read("sample_submission/eval_config.yaml").decode()
            # eval_config.yaml has evaluation: timeout_seconds, max_tool_calls, max_time_minutes, max_turns
            # No compaction_interval; mark unknown.
        except KeyError:
            pass

        # M6.7: Dockerfile.sandbox
        docker_text = zf.read("docker/Dockerfile.sandbox").decode()
        m = re.search(r'^FROM\s+(\S+)', docker_text, re.MULTILINE)
        if m:
            cfg["docker_image_name"] = m.group(1)

        # M6.8: agent.yaml
        agent_text = zf.read("sample_submission/agent.yaml").decode()
        agent = parse_simple_yaml(agent_text)
        adapter = agent.get("adapter")
        cfg["model_adapter_set"] = [adapter] if adapter else None

        # M6.10: sampling.yaml
        sampling_text = zf.read("sample_submission/configs/sampling.yaml").decode()
        sampling = parse_simple_yaml(sampling_text)
        try:
            cfg["thinking_budget_effective"] = int(sampling["thinking_config"]["thinking_budget"])
        except (KeyError, TypeError):
            pass

    rec = {
        "task_id": "*",
        "m6": cfg,
    }
    with OUT_PATH.open("w", encoding="utf-8") as out:
        out.write(json.dumps(rec) + "\n")
```

The script doesn't need PyYAML (which isn't installed). A ~15-LoC parser handles the four files because they use only:

## Implementation caveat: patches are not `git apply` compatible

The dataset's patches encode empty context lines as a bare `+` character (with no trailing space). Git's `git apply` rejects this format as `error: corrupt patch at line N`. GNU `patch` (the POSIX tool) accepts it.

| Tool | Empty context line | Result |
|---|---|---|
| `git apply --check` | `+` (bare) | ❌ "corrupt patch at line N" |
| `patch --dry-run -p1` (GNU) | `+` (bare) | ✅ applies |
| `git apply --check` (strict) | `+ ` (with trailing space) | OK — but the dataset doesn't use this form |

M4.11 was therefore implemented with `patch --dry-run -p1` rather than `git apply --check`. This is a real compatibility finding that any tool downstream of the BCF agent must respect.

## 4. Algorithms to research (8 families, mapped to findings)

### 4.1 Code localization (F3, F4)

The F4 finding (graph nodes lack file paths, embeddings degenerate) means the standard "embed the problem, find nearest code" recipe fails. The alternatives:

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **BM25 / TF-IDF over problem_statement → code chunks** | Primary localization when no symbols/files are named | Robertson/Zaragoza 2009 | Cheap, no training, surprisingly effective when the problem statement is dense (only 6/129 tasks name files). |
| **Symbol-anchored graph traversal** | When the problem names a class/function, walk `get_code_neighbors` from that symbol | Standard graph-walk | The graph has 2,500–7,000 nodes per task; 700–4,300 edges. A BFS of depth 3 from a named symbol visits ~10–100 nodes. |
| **Subgraph extraction by call-distance** | For multi-bug tasks, find the smallest common ancestor | Standard graph-algorithm | F2P ≥ 2 often means two bugs in the same call chain — a minimum-vertex-cut style algorithm finds both. |
| **Dotted-name → file heuristic** | Map `data.textends/python.py.File.Class.method` → `python.py` | Custom (no paper) | F4 fix: split the node name on `.` and check each prefix against the file tree. ~70 % hit rate by inspection. |

### 4.2 Patch synthesis (F5, F6, F7)

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **Single-hunk minimal diff** | The 55/129 (43 %) single-shot tasks want ≤ 1 hunk, ≤ 5 added lines | Standard `diff -u` | Trivially produced by `edit_file`. The v1 should default to this and only escalate. |
| **Multi-bug decomposition** | The 49/129 (38 %) multi-bug tasks need 2+ coordinated edits | Zhang et al. 2024 (AutoCodeRover) §4 | Decompose by call-graph locality: bugs that share a file should be a single edit; bugs in different files are independent edits. |
| **Test-first patch (TDD-reverse)** | When the test_patch is the spec, read it first to anchor the change | Standard TDD | The test_patch is in the dataset but **not visible to the agent**. v1 must work without it. The algorithm instead: extract function/class names from `problem_statement` and treat those as the target. |
| **Hunk-count budget** | Cap the agent at N hunks per edit | Hard rule (custom) | With 60 s wall-clock and 10 tool calls, the agent can afford ~1 hunk per edit and 3 edits. |

### 4.3 Retrieval over the F3-degenerate graph

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **Symbol-graph-breadth-first** | Walk from a named symbol through `get_code_neighbors` for K hops | Standard BFS | For tasks that name a class/function (the 6 % that name a file, plus the ~30 % that name a symbol). |
| **Subgraph-by-keyword** | Search the graph nodes for dotted names containing problem keywords | Standard text search | Node names ARE the symbol path: `fastapi.utils.DontInjectTheMiddleware`. A keyword search on these is more reliable than embedding search. |
| **PageRank on the code graph** | Find central/important files in the graph | Standard PageRank | Useful for F4's "where do I start?" — the page's most-connected files are typically where the bug is, even without an explicit query. |

### 4.4 Memory / context compression

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **Breadcrumb-journal** (W6 Reflexion-style) | Compress old turn context into "Ruled out / Next" lines | Shinn et al. 2023 | F1 budget (60 s) makes full-history replay impossible; a breadcrumb journal keeps the most recent reasoning. |
| **Spec-anchored context window** | Pin the Phase 1 spec at the start of every subsequent prompt | Older: ReAct §3 | The spec is the only stable reference; other context can be rotated. |
| **Three-tier summary** | Recent turns verbatim, middle turns in 1-line summaries, oldest turns omitted | Custom | At 50 turns × ~500 tokens = 25K tokens, summarization is needed. Three tiers give a smooth degradation. |

### 4.5 Self-critique / verification (F5, F6)

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **Pre-submit patch dry-run** | Run `patch --dry-run -p1` before `submit_patch` | Standard `patch` | F6 — 9/129 gold patches are too malformed even for GNU `patch`. The agent must do the same. |
| **Pre-submit no-tests check** | Verify the diff doesn't touch `tests/` or `conftest.py` | Custom (1-line `git diff --stat`) | F5 — 100 % of gold patches respect this; the agent must too. |
| **py_compile gate per edit** | Run `python -m py_compile` after each edit_file | Standard `py_compile` | F4.7 confirmed — 100 % of gold patches parse. Use as a real-time parse check; budgets 1 tool call per check (only do it before final submit). |
| **Targeted pytest run** | Run pytest -k on a single F2P test name | Standard `pytest -k` | F1 — only 10 tool calls total, so use them on the targeted tests extracted from `problem_statement` + `test_patch` (via the scorer-only M5.5 capture). |

### 4.6 RL / alignment for the LoRA (F2)

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **DPO on (good trajectory, bad trajectory) pairs** | Adapt tool-selection behavior | W13 | The F2 adapter is rank-4 layer-0 — too small for SFT-style code-learning. DPO on trajectory preference data fits the parameter budget. |
| **GRPO with verifier reward** | Train the adapter to prefer trajectories that pass the test | W14 | The verifier is `pytest -k` exit code. Group baseline = 4-8 trajectories per task. |
| **RLVR (RL with Verifiable Rewards)** | General framework — verifier is F2P test pass | W14 §3 | When the verifier is binary (test passes or doesn't), RLVR is the cleanest formulation. |

### 4.7 Patch scoring (post-edit but pre-submit)

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **Parse-OK score** | Already captured (M4.7) | Custom | 100 % pass rate on gold patches; the agent's score should match. |
| **Apply-OK score** | Already captured (M4.11) | Custom | 93 % pass rate on gold; the agent should target ≥ 95 %. |
| **Test-pass probability** | Probability that the patch turns the F2P tests green | Standard | Requires the vLLM eval to measure; bake into the M6 metric. |
| **Patch-size penalty** | Smaller patches score higher (less likely to break regressions) | Custom | F7 — 43 % of gold patches are ≤ 5 lines. Agents that produce bigger patches should be penalized. |

### 4.8 Termination / progress detection

| Algorithm | Purpose | Source / paper | Why this one |
|---|---|---|---|
| **No-progress detection** | If two consecutive tool calls return identical results, the agent is stuck | Custom (W6 inspired) | F1 — wasted calls are the #1 budget leak. |
| **Breadcrumb-driven early submit** | If the breadcrumb says "fix is in file X, line Y" and the edit applied, submit | Custom | Skip verification if budget is exhausted. |
| **Reversal-of-edit detection** | If a subsequent edit_file on the same file at overlapping lines reverts the prior change, abort | Custom | M4.5 — the wish list's "oscillation" metric. |

### 6.3 The 2 pre-flight decisions (Phase 0)

**Decision A: fast or slow path?**

```yaml
# Pseudo-code in the system prompt (or a skill):
fast_path = (
    m5.multi_bug_indicator is False        # not multi-bug
    AND m4.final_added_lines ≤ 5           # small diff
    AND m4.final_files_changed ≤ 1         # 1 file
)
```

For the 129-task training set, fast_path fires on:
- 0 multi-bug + ≤ 5 added lines + 1 file
- Approximate count: 56 tasks (43 %) match this exactly. The other 56 % go slow path.

For the hidden test set, this heuristic will mis-fire occasionally. That's acceptable — the slow path still works.

**Decision B: invoke `code_analyzer` sub-agent?**

Only in slow path AND only when `m5.multi_bug_indicator` is True AND the problem_statement does not name a file. The sub-agent eats ~3 tool calls (it's an agent_tool call).

### 6.4 The 3 pre-submit gates (always run before `submit_patch`)

```yaml
# Skill: pre_submit_check
inputs: { candidate_patch: str, changed_files: list[str] }
steps:
  1. Parse candidate_patch for `tests/` or `conftest.py` in any path. FAIL if present.
  2. Write candidate_patch to /tmp/p.diff.
     Run: bash -lc "patch --dry-run -p1 -i /tmp/p.diff" inside the snapshot dir.
     FAIL if exit code != 0.
  3. For each changed .py file: write to /tmp/<file>.py, run python -m py_compile.
     FAIL if any file fails to parse.
  4. Return: { ok: true } if all gates pass; else { ok: false, reason: <gate> }.
```

These three gates are the **hard rules** the wish list's M4.7, M4.11, and M5.9 fields measure. They cost 0 tool calls if the agent invokes this skill via `agent_tool`, or 2 tool calls if invoked directly via `run_command`.

### 6.5 The system prompt (system.md, 60 LoC)

```
You are an expert autonomous software engineer. Resolve the issue efficiently
in ≤ 5 tool calls. Budget: 10 calls, 50 turns, 60 s.

## Workflow
1. SPECIFICATION (0 calls). From the problem statement, extract:
   - target_file: any .py file named in the statement (rare)
   - target_symbol: any class/function name mentioned
   - symptom: what the user says is broken
   - expected: what the user expects after the fix
   Write these as bullet points at the top of your reply.

2. LOCALIZATION (0–3 calls). If you have a target_file, read_file that file.
   If you have a target_symbol, call get_code_neighbors with the symbol.
   If neither, call get_code_subgraph with a 2-hop query.

3. EDIT (1–3 calls). Use edit_file with the minimal possible diff.
   One hunk. ≤ 5 added lines. Stay in source files, never tests/.
   If multi-bug (multiple symptoms), one edit per bug, file-locality grouped.

## Verification Gate (always, before submit)
Call skill:pre_submit_check with your candidate patch and changed file list.
The skill runs py_compile, patch --dry-run -p1, and tests/-touched check.
If pre_submit_check returns ok: false, FIX the failure and re-verify.

## Hard rules
- Never edit tests/, *_test.py, test_*.py, conftest.py.
- Never run bare pytest. Use pytest -k <name> for a single test.
- Never exceed 10 tool calls. If you have 3 left, stop searching and edit.
- Never submit an empty patch.
```
