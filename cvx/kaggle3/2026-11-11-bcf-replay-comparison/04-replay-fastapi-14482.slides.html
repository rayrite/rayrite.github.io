Two layers, one symptom: how the config gets lost

issueThe whole problem statement

🐛 Fix handling arbitrary types when using `arbitrary_types_allowed=True`

Related to https://github.com/fastapi/fastapi/discussions/14184,
https://github.com/fastapi/fastapi/issues/14483

No reproducer, no traceback, no root cause. A response model with model_config = ConfigDict(arbitrary_types_allowed=True) and a field of a plain custom class (a fake numpy array carrying WithJsonSchema/PlainSerializer metadata) fails in FastAPI with PydanticSchemaGenerationError — while pure Pydantic handles the same model fine. The agent must derive both defects from code.

codeThe two loci — base commit, fastapi/_compat/v2.py [R]

# layer 1 · ModelField.__post_init__ (lines 85–99)
self._type_adapter: TypeAdapter[Any] = TypeAdapter(
    Annotated[self.field_info.annotation, self.field_info]
)   # ← no config= argument; metadata not splatted

# layer 2 · get_model_fields (lines 414–418)
def get_model_fields(model: Type[BaseModel]) -> List[ModelField]:
    return [
        ModelField(field_info=field_info, name=name)
        for name, field_info in model.model_fields.items()
    ]   # ← model.model_config never forwarded

maskWhy the first error hides the second — the masking mechanism

symptomPydanticSchemaGenerationError at TypeAdapter construction
fix L1 onlyadd config param (default None) + config=self.config
re-runerror is BYTE-IDENTICAL — config is still None
revealthe producer, get_model_fields, drops model_config
fix L2propagate config per field → behavior changes

The exception fires inside __post_init__ when FastAPI clones the response model, before the propagation gap in get_model_fields can be observed as a separate failure. A "correct" local edit to the adapter changes nothing observable — the worst kind of misleading evidence: it looks like the edit was wrong, when it was merely incomplete. The reference patch also splats the metadata (*self.field_info.metadata into the Annotated args — the v6 deck's "layer 2") so WithJsonSchema/PlainSerializer apply explicitly; that is a third component of the same construction defect, co-located with layer 1.

ruleThe propagation rule (the regression-critical nuance)

Config applies to every field except when the field type is itself a BaseModel, dict, or dataclass — those carry their own config and must not be overridden. Reference: if lenient_issubclass(type_, (BaseModel, dict)) or is_dataclass(type_): model_config = None else: model_config = model.model_config. Blanket-propagating the parent config to nested models is a regression the broader response-model tests would catch. Keep the Pydantic ≥ 2.12 UnsupportedFieldAttributeWarning suppression.

testsAcceptance: 3 tests, one new file [R]

tests/test_arbitrary_types.py (141 lines, absent from the sandbox): test_get (GET / serializes custom_field → [1.0, 2.0, 3.0]), test_openapi_schema (OpenAPI shows the WithJsonSchema array), test_typeadapter — a Pydantic-only control proving the user's model is already correct. All three must pass; the control passes even with no patch, which is what makes naive's "1 of 3" so hollow.

The concepts, explained kindly [R]

Teachable moments

Error masking
one defect's failure conceals a second, independent defect; fixing the first reveals — or fails to change — the observable failureHere the strong form: fixing layer 1 leaves the error byte-identical, because the new config parameter defaults to None until the producer forwards it. A fix that stops at layer one is still wrong.in this deck: TypeAdapter-without-config (85–99) masks get_model_fields-drops-config (414–418). The v6 deck's config-vs-metadata framing is a second, co-located masking pair inside __post_init__.
Symptom vs root cause · the 5 whys
a symptom is an observable failure; the root cause is the exact decision that produces it — ask "why" until the answer is a line of codeWhy schema error? → the adapter can't schema-generate FakeNumpyArray. Why? → arbitrary_types_allowed isn't in the adapter's config. Why? → TypeAdapter is built with no config argument. Why? → ModelField never receives one. Why? → get_model_fields drops model.model_config. Root: a propagation gap, not a missing whitelist.in this deck: the error message stops at why-2 and tells you to set a flag the user already set. The 5-whys chain walks past the message to the producer.
Belief state under misleading evidence
the agent sees clues, never truth; acting well = updating a probability distribution over hypotheses, not reacting to the latest stringAfter a correct layer-1 edit, the unchanged error is evidence FOR "a second locus exists", not FOR "my edit was wrong". The naive update (revert, re-edit the same lines) is exactly backwards.in this deck: R1 is the failure branch where the current brain makes the naive update; the producer grep and the mechanism sentence are the correct update made cheap.
Entropy & the value of a "failed" fix
entropy = how many ways your belief can still be wrong; a result's value is the part that changes your next actionA repair cycle whose fix fails but reveals layer 2 is INFORMATION, not waste: it collapses "where is config lost?" from ~5 plausible loci to 1. The waste is only in repeating an identical call whose outcome you can already predict.in this deck: the executed strike machinery formalizes this — a struck locus is entropy permanently removed from future anchor searches ("Struck loci excluded: 1").
DAG of fixes · topological order
a dependency graph with no cycles; a topological order respects every arrow — you cannot apply a consumer before its producer existsimports → dataclass field → __post_init__ (consumer) → get_model_fields (producer). Passing config= to a dataclass without the field is a TypeError.in this deck: the executed apply demo landed the producer hunk ALONE and check still said PASS — a DAG violation masked by a green syntax gate. The repro is the only oracle that sees order.
Test overfitting
code that satisfies the visible signal but not the contractBlanket arbitrary_types_allowed "fixes" the repro while overriding nested models' own configs; a one-call-site schema patch passes get but fails openapi; editing tests is discarded by the scorer outright.in this deck: all three symptom-fixes in slide 4's table are overfits. The acceptance set encodes the mechanism: propagation + exclusion + metadata, on both call paths.
Control experiment · blame the right layer
before fixing, run the thing that works outside the suspected layertest_typeadapter builds the same model in pure Pydantic and passes — proving the user's model is correct and the leak is FastAPI's plumbing. The agent can run this control itself in /tmp in one call.in this deck: naive "fixed" the already-correct repro model (v6 N3–N7); the control would have saved it the wrong-layer edits. Credit: v6's best insight.
Gate vs grader
a gate checks necessary conditions (syntax, hygiene, non-empty); a grader checks sufficient ones (behavior against the contract)CHECK: PASS means "nothing structurally wrong with submitting", never "the bug is fixed".in this deck: the executed producer-only apply passed the gate and would fail at runtime.
