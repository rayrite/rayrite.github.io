# Unit Test Plan — MYSG OT-Standby Sep 2026 Changes (INC1444350)

**Scope:** Sep 2026 priority-change time codes for Malaysia (A60) Standby Allowance (3070-3100)
and Shift Activate (3130/3140), and Singapore (A00/A80) PH-gated Overtime (3010/3030), plus the
widened Singapore Shift Allowance vs Standby same-day check (86000286), as defined in
`docs/PATCH_PLAN_INC1444350_MYSG_OT_STANDBY_SEP26.md` and implemented in `patched/PAYEDIT2A.SQL`
/ `PAYEDIT2C.SQL` / `PAYEDIT_PTA_2A.SQL` / `PAYEDIT_PTA_2C.SQL` (procedure `msg_checks`,
`msg_ot_edit_exempt`) and ported into `patched/UNIT_EDIT.bdy`.

**Scripts:** all 25 tests are **standalone**, F5-runnable `.sql` files in this same folder
(`docs/UTP_INC1444350/T-1444350-{MY|SG}-NNN.sql`) — each file fully inlines the CV-LCD-GVR
report body (worker info, leave balances, timesheet grid, simulation output table) with zero
external file dependencies. The report body is extracted **directly** from
`cvx_deluxe_harness/v2/CVX_01_REGULAR_TIMESHEET_DELUXE_v2.sql` (the v2 standalone spec template
— see `cvx_deluxe_harness/v2/README_v2_TEMPLATES.md`) by `gen_1444350_standalone.py`, which lives
alongside these scripts in this same folder; regenerate with:
```
cd docs/UTP_INC1444350 && python gen_1444350_standalone.py
```
Because the generator reads the body straight out of the v2 template file (not a cached copy),
these scripts are guaranteed to match the v2 spec byte-for-byte, including both bug fixes
documented there (no `lcd.worker.profile` reference; `l_contractor`/`l_long_day` sized
`VARCHAR2(100)`).

**Harness:** `LCD.time_edits_validation`, `p_edit_type='I'` (matches the AVCP precedent — this
also exercises `leave_check`/`future_check`, which is expected to produce no interference with
the reason codes under test here). Reason codes 86000290-86000299 (and 86000286) come from
`validate → msg_checks`.

## PTA path — `T-1444350-PTA-{MY|SG}-NNN.sql`

report body **directly** from `cvx_deluxe_harness/v2/CVX_02_PTA_TIMESHEET_DELUXE_v2.sql` — the
v2 PTA spec template, CURRENT + ORIGINAL timesheet grids, same week.

**PTA-specific configuration:**
- `v_week_end = '20260821'` (the PTA week-ending date supplied for this ticket)
- `v_edit_type = 'C'` — the only edit type the production PTA path actually sends (per the v2
  PTA template's own header note), unlike the regular-path tests above which use `'I'`
- ORIGINAL (`b_array_*`) is set **identical** to CURRENT (`p_array_*`) in every test: verified
  directly against `patched/PAYEDIT_PTA_2A.SQL` that `msg_tally` is hooked into `tally()` only
  (line ~1071) and **not** `ptally()` — so none of the INC1444350 reason codes can ever be
  affected by what the ORIGINAL array contains. Making the two identical is a genuine zero-delta
  baseline (not a workaround), which also keeps `leave_check` silent so every finding in the
  Simulation Output table is attributable to `msg_checks` alone.

The ID/script/category/expected mapping is 1:1 with the regular-path table above — e.g.
`T-1444350-MY-011` (regular) and `T-1444350-PTA-MY-011` (PTA) exercise the exact same
3100+8000+3080-same-day scenario, just through the two different call paths. See the two tables
above for the full scenario list; substitute `T-1444350-` → `T-1444350-PTA-` in the ID/filename
column to get the PTA equivalent of any row.

## Known coverage gap — Check 295 via the UNIT_EDIT.VALIDATE path

Scripts T-1444350-MY-009/010/011 exercise the CATS/PTA harness (`LCD.time_edits_validation`),
which is the only path that can see PH(8000) (an hours-type code) alongside the unit-flagged
Standby codes. `UNIT_EDIT.bdy`'s own port of the Malaysia Standby rules (used by the separate
`LCDUnitEdits` / `UNIT_VALIDATION` calling path) intentionally omits Check 295, since that path
never receives hours-type rows at all — see the comment above `msg_org_my` in
`patched/UNIT_EDIT.bdy` and `docs/QUALITY_AUDIT_INC1444350.md` for the full writeup. No test
script exists for "3100 without PH via UNIT_EDIT.VALIDATE" because the correct, intended behavior
there is that Check 295 **never fires** through that path (not a pass/fail scenario, but a
structural limitation) — checks 290-294/296-298 and the widened 286 are fully portable and should
be spot-checked against that path using an equivalent direct call to `UNIT_EDIT.VALIDATE` if/when
a harness for that entry point exists (none was available in this workspace to build one against).
